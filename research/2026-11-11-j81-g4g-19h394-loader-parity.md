# J81 G4G firmware: 19H394 and 19H422 comparison

Offline follow-up using the local 19H394 kernelcache, the independently
extracted G4G firmware kext and the earlier 19H422-associated cache. No device
access or firmware execution. The A9 extractor's top-level command stopped
because 19H394 lacks its hard-coded `IOGPUFamily` dependency; its two G4G
kexts had already been extracted before that failure. The selected file is
therefore treated as a partial extractor output and checked below rather than
as a complete extractor manifest.

The 19H394 firmware kext's `__TEXT,__const` is `0x1cbb4` bytes at virtual
address `0xfffffff0059ab9c8`. Its code at `0xfffffff0069820c0` stores that
address through its first output pointer, stores `0x1cbb4` through its second,
and returns 1. The kext's `__DATA_CONST,__const` contains a reference to this
method once. This supports that the extracted section is the static firmware
return span, not a runtime trace of the live object or a validated firmware
signature. Apple-derived files and decoded instructions remain private.
The 388-byte firmware kext executable section has one byte-identical match in
the 19H422-associated kernelcache.

Both 117,684-byte firmware sections have 88 LDR records, and our parser's
complete ordered metadata reports agree: load/zero addresses and lengths,
configuration pairs and thread entries. The 19H394 metadata was also
[cross-checked](2026-11-11-j81-ldr-crosscheck.md) against the independent A9
META decoder. The two payloads are **not** byte-identical: exactly 13 bytes
differ. Eleven are inside a single load record's 20-byte printable field
containing a time-shaped string; the remaining two are that record's trailing
L2 checksum bytes. This localization does not validate the checksum or prove
that the field is semantically irrelevant. It supports using the current
19H394 span for loader preparation without assuming an older image is
byte-identical. It does not establish an executable, compatible or authorized
firmware boot path.

## Bounded clock-path round

The A9 team's documented GFX record fields decode J81 state 1's known
`0x6436d063` consistently with the previously recovered 365 MHz table entry;
the same A9 notes say their GFX PLL lock/frequency readback was not known.
On J81, the 19H394 iOS capture and Linux report the same sampled state-1
table words and perf control, while page-5 `+4` bit 30 differs. The later
DWI-first and 20-domain runs updated the candidate PMU row, yet the bit stayed
clear and the 20-domain core read did not return. None establishes that this
page is the GFX PLL or that bit 30 is its lock signal. The current evidence
does not identify a concrete additional software write before the iOS ID read.
A broad new iOS trace or another guessed write is therefore not ready for a
hardware round. The useful next offline question is which boot-stage or
hardware configuration drives the page-5 status, with the actual running
19H394 image and cross-OS readback where justified. A measured difference
must be separated from a proven prerequisite.

REA opened the locally reconstructed Mach-O, but Ghidra did not create a
function or decode instructions at the candidate method address in that
session; the bounded instruction observation above was checked with the
Mach-O disassembler instead. REA was closed. This limitation does not rule out
other tooling or runtime dispatch.
