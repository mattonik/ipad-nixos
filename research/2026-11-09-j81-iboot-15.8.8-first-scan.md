# J81 iPadOS 15.8.8 LLB/iBoot: decrypted, first constant scan (2026-11-09)

The captured Linux FDT reports `iBoot-7459.140.15`, matching iPadOS
15.8.8; earlier notes only covered iOS 8.1 (`iBoot-2261.3.32`). Both are now decrypted. The
images and keys stay private (NAS `firmware/iboot/`, README there); nothing
from them is in Git.

## How

- BuildManifest of `iPad_64bit_TouchID_15.8.8_19H422_Restore.ipsw`: both
  `j81ap` identities (chip `0x7001`) use `LLB.ipad5b.RELEASE.im4p` and
  `iBoot.ipad5b.RELEASE.im4p` (E).
- iPad in DFU, `gaster pwn` (Nix `packages.aarch64-darwin.gaster`), then
  `gaster decrypt_kbag` on each production KBAG with the device GID, then
  AES-256-CBC. Both outputs carry the `iBoot-7459.140.15` banner (E).
- 8.1 images re-decrypted with the public 12B410 keys for the comparison.

## Constant scan (MMIO `0x200000000`–`0x20fffffff`)

Scanned all four images for constants built with `movz`/`movk`, `add`
immediates and 64-bit literals (capstone, whole image).

- **No GPU block.** None of the four images has a constant in
  `0x201000000`–`0x201ffffff` (RGX, GPC, bridges); no direct
  constant-address GPU access was found in either version.
  Dynamic address calculations or missed paths remain possible (E for the
  bounded scan).
- **15.8.8 LLB writes the GFX perf table** in a helper at image offset
  `0x10310`: word to `0x20e01c000 + n*0x10`, then a byte from the entry's
  `+0x10` field to `+4`. That is the layout read live on 2026-11-09,
  including the `0x70`/`0x80` `+4` words (E).
- `0x20e01c200` and `0x20e01c300` are not built as constants in 15.8.8 LLB
  (they are in 8.1 LLB); the live values match 8.1's, so 15.8.8 likely
  writes them through a base-plus-offset or table path (I).
- Both LLB versions write `0xffffffff` to eight words at
  `0x20e104100`–`0x20e10411c` and store per-index words at `0x20e104180`.
  This block is near the `sgx` node's `meta-sw-interrupt` addresses
  (`0x20e104010`/`0x090`); its purpose is unknown (U).

The 15.x compiler builds many addresses from a block base plus offsets, so
a constant-level diff against 8.1 is noisy (many 8.1 constants "disappear"
without the access disappearing). A real write inventory of 15.8.8 needs a
Ghidra pass with the image bases resolved; this scan does not rule out
GPU-block accesses through computed addresses.

## Ghidra pass (same day)

All four images analysed headless (Ghidra 12.1.4, raw AArch64, an
uninitialised `MMIO` block at `0x200000000` so computed addresses resolve).
Load addresses come from each image's own relocation literal at `+0x300`
and check out against string pointers: LLB `0x180380000` (both versions),
iBoot `0x870000000` (15.8.8) and `0x87a17b000` (8.1). The 2026-11-08 notes
used other bases for 8.1, so their absolute addresses are offset; their
offsets within the image and register addresses are unaffected. Writes
found: 8.1 LLB 489 addresses, 15.8.8 LLB 464, 8.1 iBoot 186, 15.8.8 iBoot
191.

| Area | 8.1 LLB | 15.8.8 LLB | 8.1 iBoot | 15.8.8 iBoot |
|---|---|---|---|---|
| GPU block `0x201xxxxxx` | none | none | none | none |
| GFX perf table `0x20e01c000`/`+4` | write | write | — | — |
| `0x20e01c200` | write (bit 31) | **none found** | `str wzr` (quiesce) | `str wzr` (quiesce) |
| `0x20e01c300` | write `0x40000001` | **none found** | — | — |
| GFX PS `0x20e020320` | — | — | — | — |
| `0x20e104100`/`104`/`180` | write | write | write | write |

The 15.8.8 perf-table builder (`0x180390180`, decompiled) copies up to 12
template entries (states 1-12) into the table through the helper at
`0x1803902e8`. On chip `0x7001` it can drop two of them, and it pads the
tail with the empty entry 0. That matches the live table: states 1-8
valid, 0 and 9-15 zero.

**Open finding.** No write of `0x20e01c200` or `0x20e01c300` was found in
15.8.8 LLB, neither as a resolved reference nor as a raw constant or table
encoding (byte searches for the address, the offset and `>>4`/`>>8` forms
came up empty). Yet the live values (`0x80000000`, `0x40000001`) equal
what 8.1 LLB writes. Either 15.8.8 sets them by a path this analysis
cannot see, or they are hardware reset values (U). Which LLB actually runs
on our checkm8/palera1n DFU boot has also not been shown directly (U).

Other writes that differ between versions (addresses only, purpose not
traced): 15.8.8 LLB adds `0x20e0202a8` (a PMGR power-state word),
`0x20e029054`, `0x20e300000`, `0x200000904`, `0x200001000` and per-cluster
words at `0x20e4x01c0`/`01bc`/`0700`; 8.1 LLB has `0x20e027000`-`0c`,
`0x20e029034`, `0x20e100010`, `0x20da010xx` and `0x20a11001x` that 15.8.8
LLB lacks. None is in the GPU block.

Result: these scans found no 15.8.8 bootloader GPU-block or GFX
power-state accesses; computed or otherwise unresolved paths may be missed.
One GFX-related difference from 8.1 is
that 15.8.8 LLB no longer visibly writes the perf control words.

## Which iBoot booted our Linux runs (same day)

The Linux FDT captured on 2026-11-09
(`artifacts/live/private/j81-fdt-20261109-current.dtb`) has
`/chosen/asahi,iboot2-version = "iBoot-7459.140.15"` (E). m1n1 copies this
from the ADT's `/chosen/firmware-version`, which PongoOS overwrites with its
own name at start and restores to the original value in `bootm` (both E in
source). The value is consistent with the 15.8.8 iBoot image decrypted above,
but firmware-version metadata is not an execution trace: it does not prove
when that iBoot ran relative to DFU or PongoOS. The ADT carries no
`system-firmware-version` here, so the LLB build is not reported (U).

Consequence: the live `0x20e01c200 = 0x80000000` and
`0x20e01c300 = 0x40000001` were observed in a boot reporting 15.8.8 iBoot
metadata. No write
of either was found in the 15.8.8 LLB scan. A missed code path, another
boot stage, retained state, or reset values are possible (U). The 8.1
writes remain a comparison, not proof of what ran on this boot.

## The `0x20e104100` block is the AIC, not the GPU (2026-11-09)

The ADT `/arm-io/aic` node has `reg` base `0x20e100000`, size `0x100000`
(`aic,1`), so `0x20e104000` is AIC offset `0x4000` (E). Against the AIC1
layout Linux uses (`irq-apple-aic.c`: SW_SET `0x4000`, SW_CLR `0x4080`,
MASK_SET `0x4100`, MASK_CLR `0x4180`, one bit per IRQ, 32 IRQs per word):

- The bootloaders' all-ones writes to the eight words `0x20e104100..0x11c`
  are MASK_SET for IRQs 0-255, i.e. "mask every interrupt". The stores at
  `0x20e104180+idx` are MASK_CLR, unmasking the IRQs they use (I, by
  layout). Ordinary bootloader IRQ housekeeping, not GPU setup.
- `meta-sw-interrupt` is in the `sgx` node (checked: it sits between the
  `vxd` separator and `name = sgx`, E). Read as 64-bit addresses it is two
  records `{set 0x20e104010, clear 0x20e104090, mask}` with masks `0x40`
  and `0x400` (E). Word `0x10/4 = 4` covers IRQs 128-159, so the bits are
  IRQ 134 (`0x86`) and IRQ 138 (`0x8a`), the first and last of the `sgx`
  `interrupts` list `0x86..0x8a` (E). This independently confirms the AIC1
  layout reading above.

So the GPU's "meta" software interrupts are AIC software-trigger bits on
two of its own IRQ lines, which the iOS GPU driver can raise and clear
itself. None of this touches the GPU block or explains the core-ID hang.
Linux's AIC driver masks interrupts during probe, but its later per-IRQ
state has not been compared with iOS at the GPU identity read (U).
