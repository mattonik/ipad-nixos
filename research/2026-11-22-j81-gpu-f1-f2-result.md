# J81 GPU F1/F2 run result (2026-11-22, boot 21:28 DFU, module sha256 11111c1e…)

Run: j81_gpu_run.py --write w1 --write w2a --write f1 --write f2, watchdog-supervised, fresh boot, preflight GO, user "go".

Observed (console.log, private logdir artifacts/live/private/j81-gpu-run-20261122-f12-run1):
- precheck, pmgr, activate, batch, W1, W2a all passed exactly as in earlier runs (core=0x00070500, id=0x011b0803, w2a_set=0x0000f1fb6c000000, w2a_clear=0).
- The log ends at `stage=before-write-f1` + `READ`; no `after-write-f1` line. The runner reported INCOMPLETE; 25 s later the iPad did not answer ping (watchdog reset). So F1 hung the bus. F2 never ran. No ConfigRAM replay evidence was obtained.

What the hang is NOT yet known to be: the log cannot say which access in step_f hung. Candidates (hypotheses, not observed):
1. Our poll bound is 30 ms (3000 x 10 us) whereas stock polls up to 30 s. If the 1->0 transition (+0x1000 <- 0x10, wait bit 4 clear) takes longer, step_f jumps to `out:` and still reads RGX 0x3800/0x3804/0x3808/0x20 while GPC is in state 0. Packet 8 says RGX may only be read in state >= 1; such a read in a gated state would hang the bus. This is a defect in our step (reads must be skipped on any timeout), independent of whether Fender behaves as described.
2. The state-0 write or later ConfigRAM/0x20000 writes themselves wedge the power controller.
3. The state 0 -> 1 transition never completes.
Not distinguished. The framebuffer breadcrumbs (crumb=on) were not used in step_f, so no on-screen hint exists.

Next (needs a fresh DFU boot; do not retry this boot): fix step_f to never read RGX unless the final state is verified 1 (and bound the polls like stock, 30 s only where watchdog allows: feed is per step, so use a short bound and report), add fb_crumb marks and a GPC_STATE readback log between sub-steps, and run F1 alone first.

## Fourth run: g0..g4 (module 596fa38c…), fresh boot — the 1 -> 0 -> 1 cycle WORKS when the first read is delayed

Observed (private logdir j81-gpu-run-20261122-g-run1; supervisor finished rc=0, watchdog disarmed, iPad still reachable afterwards):
- g0 (write +0x1000 = 0x10, nothing else): returned.
- g1 (single read of +0x1000): g_r1 = 0x00000000 (state 0, busy clear).
- g2 (bounded poll, GPC only): state 0, no timeout.
- g3 (100 ms, write 0x11): returned.
- g4 (poll, state must be 1, PLL lock check): g_poll_state = 0x00000001, PMGR +0x5004 = 0x40000000 (bit 30 set).
So the state-0 request, a read of GPC_STATE in state 0, and the return to state 1 are all safe on J81.

What differed from the three hanging runs (F1 old, F1 fixed, f1a): there the read of GPC_STATE followed the 0x10 store IMMEDIATELY (back-to-back), while here every stage boundary adds a host round trip (>> 100 us, not measured) between the store and the first read. Hypothesis, consistent with all four runs but not proven by a controlled test: a read of the Fender block immediately after the 1 -> 0 request stalls the bus until the transition settles. The batch step's immediate poll after 0x11 (0 -> 1) works, so the effect is specific to the 1 -> 0 direction.
Next: in step_f insert msleep(100) between the 0x10 store and the first poll read (and a short delay before the later polls), keep Apple's order; then F1, then F2.

## Fifth run: f1/f2 with delayed first read (module e523c79d…): F1 hangs again

So the hang is inside that span, before the +0x10 cycle / +0 store / ConfigRAM / +0x20000 (none of those can be the cause).
The "delay the first read" hypothesis (above) is therefore NOT sufficient: here the first read was 100 ms after the store and the bus still hung. What differs from the passing g-run (g0 store; return to userspace; g1 single read; g2 poll; g3 msleep(100)+0x11; g4): in the hanging runs the 0x10 store, the sleep(s), the polls and the readback all happen inside one sysfs write call, and F1 also draws framebuffer squares (fb_crumb_clear/mark) before the store and after the 100 ms wait while the GPU is in state 0 (run 1 had no crumbs but read immediately). Not yet separated: (a) a kernel-internal msleep right after the store (CPU idle), (b) framebuffer writes while the GPU is in state 0, (c) back-to-back GPC polls, (d) anything else in-call.
Next: z-steps (z0 crumb clear+mark1, z1 msleep(100) alone, z2 mark 2) interleaved with the passing g-steps to bisect.

## Sixth run: z/g bisect (module 56889477…) — ROOT CAUSE of the F1 hangs: back-to-back Fender accesses in state 0

Order run: w1 w2a z0 g0 z1 g1 g2 z3 z1 z2 g3 g4 (logdir j81-gpu-run-20261122-z-run1; first attempt aborted at argparse because zsh did not split $W — no device action, cf. memory note on zsh splitting).
Passed: z0 (crumb row clear + mark 1), g0 (0x10 store), z1 (msleep 100 in state 0), g1 (single read: 0x00000000), g2 (poll: 0x00000000).
Hung: z3 = ten back-to-back reads of GPC +0x1000 in state 0 (log ends at `stage=before-write-z3`; no ping afterwards).
Conclusion: in GPC state 0 a Fender-block access issued right after the previous Fender-block access (read after read, and, by the earlier runs, write after read / read after store) stalls the bus; single accesses separated by long gaps (host round trips, 100 ms sleeps) are safe, and so are 10 us-spaced poll iterations only while busy was set... not verified. This explains all five F1 hangs: each had a GPC read immediately after the previous GPC read (readback of g_after0 straight after the poll's last read, or a ConfigRAM store straight after it); run 5 survived the 100 ms-delayed first read and died on the immediately following readback.
Framebuffer writes and in-kernel sleeps in state 0 are SAFE (z0/z1 passed; z2 not reached). The spacing needed is unknown (somewhere between the poll's 10 us + loop overhead and the host round trip); next version spaces every Fender access in the F steps by 100 us (udelay) as a first safe-looking guess, to be tightened by test.

## Tenth run and ROOT CAUSE of runs 1-9: the host supervisor's 512-byte line buffer, NOT a bus hang (found 2026-11-24)

Repeat of the g-run (w1 w2a g0..g4, module c82c933e…, logdir j81-gpu-run-20261124-grepeat-run1): all five g steps passed, finished rc=0, watchdog disarmed. So g0 passes and h0 (byte-identical accesses) "hung" — which pointed away from the GPU.
`boot/gpu-watchdog-supervisor.c` reads every stage line with `fgets(line, 512)`; a line without a newline in the first 511 bytes makes it `fail_closed()` (never forwards, never feeds the watchdog), so the iPad resets 20 s later and the log ends at the preceding `before-` line — exactly the signature we took for a bus hang. Longest `after-` line of each run: passing g-run 463 bytes (max passing); every hung run's previous line was 390 or 463 and the line of the step that "hung" would have been longer: f1/f1a/f2 add ~190 bytes (>=580), z3 adds ~95 (~558), h0 adds ~280 (~670).
Consequence: **the F1 runs 1-8, the z3 "ten back-to-back reads hang" bisect and the "1 ms spacing still hangs" conclusion are all unsupported**; nothing shows the Fender block hangs the bus in state 0 at all. The g-run (state 0 reads, 100 ms, return to 1, PLL lock set) remains valid and now reproduced twice.
Fix: status_show() is compact once an f/h/z3 step has output and capped at 480 bytes (module 20194096…, commit after fdb2f56). Lesson: every host-side line-length limit must be checked when adding fields; add a cap whenever a fixed buffer sits in the path.
Next: rerun w1 w2a h0..h11 (F1 with an empty ConfigRAM) with the compact module; then F2 via h7b (Apple 64-bit encoding).

## Twelfth run: F2 stepwise (h0..h6, h7b, h8..h11; module 20194096…) — first GENUINE hang, at h8

Logdir j81-gpu-run-20261125-f2-run1, fresh boot, preflight GO. h0..h6 and h7b passed (h7b = the two-entry list with Apple's 64-bit encoding, stored word by word: 0x00003804 0x00035500 0x00ff3800 0x00300001 0x00ff3808 0x00000001 0xffff0000; observers unchanged: 0x3ff/0x80000000/0x100). The log ends at `stage=before-write-h8`; no `after-write-h8`; INCOMPLETE; the iPad reset (no ping, later iPadOS). Longest after-line 395 bytes, equal to F1's, so this is NOT the supervisor line-length artefact.
h8 = wmb, msleep(100), store 0 to GPC +0x20000 (core word), read the three PMGR observers. In run 11 the identical h8 passed with an EMPTY ConfigRAM (terminator only). The only difference is the two-entry list, so: with entries in ConfigRAM, the +0x20000 = 0 store (or the PMGR reads after it) hangs the bus in GPC state 0.
Reading (I, one run): the core-word store makes Fender start consuming the ConfigRAM list while GPC is still in state 0, so its RGX register write (SLC 0x3800) goes to an unpowered/ungated block and stalls the bus; or one of the entries is wrong for J81. This contradicts the assumption that replay happens only at the 0 -> 1 transition. Apple's own order is the same (list, +0x20000 = 0, then 0x11) and works on iPadOS, so either the entry content/encoding differs on J81 (e.g. the high-half word `0x00003804`, a missing flag on a 64-bit reg+4 entry) or the replay happens at +0x20000 and iPadOS's first entries are state-0-safe (e.g. BIF_CAT_BASE0 first).
Next (one variable per boot): (a) a single 32-bit entry `0x00ff3808 0x00000001` only; (b) the same entry list but store +0x20000 = 0 AFTER the 0x11 request instead; (c) the Apple-style first entry (BIF_CAT_BASE0 register) alone. Needs a fresh DFU boot each.

## Thirteenth run: F2 bisect (a), ONE 32-bit entry (h7c, module f5718395…): hangs at h8 again

Logdir j81-gpu-run-20261125-f2c-run1. h0..h6 and h7c passed (list = `0x00ff3808 0x00000001 0xffff0000`; observers unchanged). Log ends at `stage=before-write-h8`, no `after-write-h8`; iPad reset; longest after-line within limits (see below). So the two-entry list's 64-bit entry is NOT the cause: with ANY non-empty ConfigRAM list, the store of 0 to GPC +0x20000 (h8) hangs the bus in state 0; with only the terminator (run 11) it passes. Reproduced twice (runs 12 and 13).
Reading (I): the core-word store starts Fender walking the ConfigRAM list immediately and its first RGX register write stalls in state 0 (RGX not reachable then); the "replay at the 0 -> 1 transition" model is wrong at least for this store, or Apple's first entries are state-0-safe. 
Next (c): skip the +0x20000 store entirely (h8n: wmb, 100 ms, observers only), then 0x11 as before. If replay happens at the 0 -> 1 transition, SLC reads 0x00320001/0x00035500/1 afterwards without ever touching the core word. If SLC is unchanged, the core-word store is what triggers replay and it must happen in state 1.
