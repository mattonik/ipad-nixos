# Review of the A8 thread's T7001 follow-up, and the iPadOS state probes (prepared 2026-11-20, none run)

## Review of the follow-up checklist against our J81 data
1. **vm_sram 0x20e023004 before/after the 0x20e02d000 |= 1 store.** Measured (Linux, J81, `2026-11-20-j81-linux-reorder-result.md`): 0x170 before any store (S0), 0x170 after MiscACG (S1), 0x180 right after the +0x2d000 store (S2), back to 0x170 after the GFX cycle and unchanged through GPC. It never reads 0, so the "stays 0 -> block not there" branch does not apply. The block responds: +0x2d000 reads back 1 and the status word +0x2d100 goes 0 -> 1 (T7000: 0x00505000 -> 0x004c5003). The address comes from the 19H394 stock kernel audit (soc-tvm group 3 rail 1 0x20e02d000, request old|1, no poll), and iPadOS reads 1 there before GPC and after page 5 (`2026-11-20-j81-ios-tvm-probe-result.md`).
2. **J81 ADT `sgx` node gates.** From the raw J81 ADT (sha256 be315828...): `clock-gates` = [0x7c], `power-gates` = [0x7c], no `devices` property; `reg` = 0x201000000 (0x100000) and 0x201e00000 (0x100000); compatible `gpu,t7001`. One gate, like T7000; no second GPU domain is described. (That 0x7c is the domain at PMGR 0x20320 was not re-derived here.)
3. **Other ApplePMGR::start writes (stock 19H394 audit, `audit_j81_pmgr_start.py`).** Besides enableACG(true) 0x20e032000 old|1 (done) and soc-tvm (done): cpu-tvm=1 rail 0 address 0x202220048 request64 old|1 (enable skips +0x50 polls); dpe-thrtl 12000 selector 8 base 0x202220000 write64 +0x1b0, +0x1a0, +0x150, +0x190 (group 22 updates +0x190 bit 35); MCC(+0x688) / voltage enable(+0x698) in the startup parent; CPU resource words at 0x202220020 / 0x202220068 / 0x202220078 (8 bytes each). The report's "PLL1/PLL4 +8 [31:30] = 01" is exactly our open page-1/page-4 difference: iPadOS requests 0x40480348 / 0x48480348, Linux holds 0x80480348 / 0x88480348 (bits 31:30 = 10). The report's 0x20e022000 bit-31 words and the ACC +0x20 RMW mask are not in our audit output; ACC +0x20 may be the 0x202220020 word above (unconfirmed).
4. **Full GPU PMGR diff on iPadOS.** Not possible with what we can build now: the KPF module source tree is not on this machine, so the probe is limited to one-word patches of the existing module (a handful of words per boot). The probes below cover the CPU TVM/DPE words and page-1/page-4; they are the part of the diff we can take.

## Probes (built by `boot/make_j81_ios_state_probes.py` from the run-3 module 0a20ead8..., hashes in `artifacts/live/private/j81-ios-state-probes/SHA256SUMS`; test `boot/test_make_j81_ios_state_probes.py` passes; patched blocks disassembled and checked)
Same boot procedure as the 2026-11-19 pre-GPC run (DFU, `sudo boot/vendor/palera1n-macos-arm64 --rootless --override-kpf <module> --debug-logging`, unlock, `sudo /usr/bin/log collect`, filter `J81_BOOT`). Read-only: every patch only changes the address of a print-only read, no store is added, the core-read gate (page-5 bit 30 at P1 F3) is untouched.
- **page14** (8 words): P0 `F=` -> PMGR +0x1008 and P0 `P=` -> +0x4008 (before GPC); P1 `F=a/b/c` -> a = +0x1008, b = +0x4008, c = page 5 +4 (after GPC and page 5, before the core read). Core ID still read. One boot gives the page-1/page-4 words at both phases: the missing iPadOS readback.
- **cpuNN** (2 words each): the core-ID mapping becomes the CPU cluster resource 0x202220000 and the single read there becomes +0xNN; `CORE=` then prints that 32-bit word (the core ID is not read in these boots). Variants: cpu48 (CPU TVM bit 0), cpu194 (DPE bit 35 = bit 3 of the high half of +0x190), cpu20 (ACC candidate), cpu190, cpu150, cpu1a0, cpu1b0 (DPE context). One word per boot, so a full DPE set is six boots; priority order: page14, cpu48, cpu194, cpu20, then the rest only if one of those differs.
Risk: reading the CPU cluster block through an ml_io_map mapping in kernel context could fault; a panic reboots iPadOS into a normal boot (as in earlier probe failures) and loses nothing else. The probes read PMGR words that iPadOS software itself reads or that Linux has read safely.
Expected use: compare each value with Linux's at the same phase (page-1/page-4 0x80480348/0x88480348; CPU words unknown on Linux, they would need a matching Linux read through /dev/mem with the existing mapping probe pattern).
