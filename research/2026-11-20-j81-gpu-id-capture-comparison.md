# J81 GPU-ID evidence by boot

The November 19 mailbox has three boots with a page-5-high sample and an attempted GPU-ID read. Each row below uses one boot. I rechecked the three result packet manifests. All addresses are physical.

| Boot (UUID prefix) | Final evidence before or around GPU-ID | Outcome |
|---|---|---|
| iPadOS 19H394, 846527FB | Pre-GPC MiscACG 1, page-5 +4 initially 0. P1 recorded 0x40000000 three times. The next two records were BEFORE CORE READ and CORE. | 0x00070500 returned |
| Linux late, 49df36fd | Last supervised reads gave GFX PS 0x3ff, MiscACG 1, page-5 +4 0x40000000, GPC state 1, GPC control 0x40000000. The last marker names 0x201000020 and width 32. | No returned word recorded. Runner reports watchdog reset. |
| Linux timed, a076f20f | GFX PS 0x3ff, MiscACG 1, GPC initially 0. The timed sequence reported poll success after 0x455 reads and page-5 +4 0x40000000, then emitted its 46-tick checkpoint. | No returned word recorded. Runner reports watchdog reset. |

Page-5 +4 is 0x20e005004. Successful sampling establishes its value only at the sample times. The iPadOS raw GPC status at poll exit is absent. Its P1 G field comes from the log buffer. Linux lacks an architectural trace of the GPU load or the following barrier completing. Its last console line cannot localize the stall to one instruction. The iPadOS BEFORE and CORE record timestamps differ by 335 counter ticks (about 14 microseconds at 24 MHz), including instrumentation. The Linux 46 ticks (about 1.92 microseconds) end before emitting the last checkpoint. These intervals have different endpoints.

## What would distinguish the remaining explanations?

* **CPU translation and first touch.** Look for a saved translation of the actual VA and its mapping attributes, or fault diagnostics tied to the target VA and boot. The pinned Linux path installs the descriptor before returning from mmap. A first access can still miss in the TLB. The retained timed checkpoint demonstrates the syscall returned, while the late checkpoint precedes the syscall. [Linux mapping trace](2026-11-20-j81-linux-gpu-id-mapping.md)
* **Device completion and barrier.** A completed-load marker or architectural trace between the load and barrier would discriminate those stages. Current logs bracket both. Moving the marker changes timing. Retrying the same sequence contributes no new discriminator.
* **Interconnect, reset and clocks.** Look for phase-matched captures of page-1/page-4 readbacks, further Fender status and named clock/reset ownership. Record widths, physical ranges and boot IDs. A requested clock value, a page-5-high sample and a GPU transaction completing are distinct observations.
* **Timing.** Favor archived operation order, counter samples with named endpoints and separately timed working boots. Current intervals cannot define a delay that would make the load succeed.
* **CPU vs GPU transactions.** This comparison concerns a CPU MMIO load. A GPU DMA mapping would need independent evidence of its relevance to the register transaction.

## Clock readbacks and execution privilege

The five records in the successful November 19 boot's NDJSON are P0, GPC timing, P1, BEFORE CORE READ and CORE. Their decoded fields do not include page-1 +8 or page-4 +8. The three P1 samples are all page-5 +4. The working probe's sequence includes 66 bridge store requests before GPC. The earlier [bridge comparison](2026-11-10-j81-ios-corrected-bridge-result.md) matched all 66 ordered requests with Linux test4. The effective page-1/page-4 pair at the successful GPU load remains unknown. Linux page-5-high observations alongside 0x80480348/0x88480348 establish those words can coexist with bit 30 high. The proposed Apple pair 0x40480348/0x48480348 comes from a separate write window. Comparing it as though it were same-boot working readback would overstate this lead.

The [November 16 bare-PongoOS result](2026-11-16-j81-pongo-core-read-result.md) supplies an earlier privileged, non-Linux attempt. The operator capture ends on the same physical address with no response, but all three immediately preceding page-5 samples were zero. This shows a stall can occur outside Linux userspace. It leaves open whether a privileged Linux access with page 5 high would succeed. The earlier archived Linux test3/test4, November 9 timed and November 11 wide-power result directories identify userspace supervisor/probe paths. I found no completed phase-matched Linux kernel-mode GPU-ID attempt in these captures or the November 19 mailbox. Generating an EL1 test would change both mapping path and privilege unless both are measured; a difference in result alone would still need attribution.

## Which difference to pursue first

Both mapping paths predict leaf AttrIndx 3 with MAIR byte 0x00 (Device-nGnRnE) for this peripheral. The working observer uses a kernel read/write mapping. Both Linux mappings are read-only user mappings, including the timed reader that opens the file read/write for the separate GPC stores. Both permissions allow a CPU load. On iPadOS and on the late Linux boot, core map creation occurs after page 5 was sampled high. Only the timed Linux boot maps before GPC. This weakens a map-order-only explanation. The timed binary has two ordinary register-immediate instructions between the load and barrier. Its console output covers neither instruction's completion. [iPadOS mapper trace](2026-11-20-j81-ios-gpu-id-mapping.md) · [Linux mapping trace](2026-11-20-j81-linux-gpu-id-mapping.md)

1. Look first for boot-matched CPU translation and fault evidence. A matching VA-to-PA result for the actual mapping and MAIR byte can test the static prediction. A saved exception PC, syndrome and valid fault address could distinguish a CPU permission/translation fault from an external abort. A watchdog reset alone supplies none of these. Generic kernel VA dumps omit the Linux user mapping, and an address-range listing does not contain its type.
2. If these agree or were never captured, prioritize working-iPadOS post-GPC register readbacks. The late Linux boot sampled Fender control 0x40000000 (bit 29 clear). The stock performance-state guard checks bits 29 **and** 30, but its execution before this successful observer read is unproven. This makes the working control word a specific archive target. Pair it with page-1/page-4 +8, extended Fender status, and timing only where the same boot actually contains them. Check CPU/SoC TVM and DPE returns against the parallel archive work. [Fender guard and its ordering limit](2026-11-17-j81-fender-ready-static-audit.md)
3. If the archives contain neither, a mapping-only Linux observer could report the actual user VMA's output PA and effective attributes, then unmap without touching the GPU. A positive result would leave CPU privilege and downstream fabric/clock/reset state open. A kernel-mode retry using default ioremap would change both privilege and memory type. A post-load change from DSB LD to DSB SY cannot demonstrate that the device responded or locate the failure. A GPU DMA/DART experiment tests a different initiator.

The stock 19H394 SGX node names the same PMGR device ID (0x7c, GFX) in both its clock-gates and power-gates properties. Its first arm-io reg range translates to 0x201000000 with length 0x100000. This independently places the 32-bit register inside that resource. The property and the observed Linux GFX PS 0x3ff describe different evidence from an acknowledged read of the core itself.
