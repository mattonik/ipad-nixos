# J81 D2207 VBUS ADC: exact completion path and minimal Linux interface

**Date:** 2026-10-11  
**Scope:** static/software analysis only; no build and no hardware access  
**Target:** iPad Air 2 J81/T7001, iOS 8.1 12B410 D2207 PMU

## Result

The VBUS ADC path is sufficiently recovered for one bounded Linux test.
D2207 ADC channel 9 measures VBUS current and channel 19 measures VBUS
voltage. A conversion starts by writing the channel and bit 7 to `0x0500`.
Completion is PMU internal vector 89: event register `0x005b` bit 1, with the
matching active-low mask at `0x007b` bit 1. Reading the event block is the
acknowledgement; Apple performs no write-to-clear operation. Once that event
has fired, Apple immediately reads two result bytes at `0x0502`.

The smallest implementation that fits the current tree is a mutex-protected,
bounded polling helper in `j81_d2207_charger.c`, exposing
`POWER_SUPPLY_PROP_CURRENT_NOW` and `POWER_SUPPLY_PROP_VOLTAGE_NOW`. This is a
temporary J81 implementation: the present generic Apple PMIC parent has no
D2207 IRQ controller. A future proper D2207 MFD driver should own the ADC lock,
event acknowledgement and interrupt completion.

## Exact transaction for channels 9 and 19

The two power-source wrappers pass flags zero to the raw ADC call. Therefore
the special preparation used only for channel 3 or callers with flag bit 0 is
**not** part of either VBUS measurement.

1. Serialize the whole ADC transaction. Apple waits while its ADC state is
   non-zero; this is not merely per-I2C-transfer locking.
2. Form a control byte from the cached control baseline, insert
   `channel & 0x3f`, set bit 7, and write it to `0x0500`.
3. Set state 1 and wait for the ADC-complete callback, with a 1000 ms absolute
   deadline. Apple does not wait a fixed delay and then trust `0x0502`.
4. The callback changes state 1 to state 2 and wakes the waiter. State 2 is
   the result-valid condition. There is no additional settling delay.
5. Bulk-read two bytes from `0x0502` and decode:

   ```text
   raw = (result[1] << 4) | (result[0] & 0x0f)
   ```

   Bits 7:4 of the first byte are status, not sample bits. Exact J81 rejects
   channel 9 if bit 7 of the first byte is set. Channel 19 ignores the upper
   status nibble and decodes the low 12 bits. This corrects the opposite
   interpretation in the older plan prose.
6. On success, timeout or I2C error, Apple reads `0x0501`, writes it back with
   only bits 2:0 retained, clears bit 7 of the saved `0x0500` control byte,
   writes `0x0500`, sets state 0 and wakes any serialized caller.

The optional path skipped by channels 9/19 sets `0x0501` bit 6 and waits up to
80 ms before starting. It must not be copied into the VBUS-only helper.

## Completion event and acknowledgement

The internal-interrupt token is `0x0b02`. Apple's token decoder computes:

```text
highest_set_bit(0x02) + ((0x0b02 >> 5) & 0x7f8)
= 1 + 88
= vector 89
```

The event block starts at `0x0050`, so vector 89 is byte `89 >> 3 == 11`, bit
`89 & 7 == 1`: **`0x005b` bit 1**. The active-low mask block starts at
`0x0070`, making the matching mask **`0x007b` bit 1**. Apple's `enableVector`
clears that mask bit.

`AppleD2207PMU::interruptAction` calls `readEvents`, which performs one
14-byte read of `0x0050..0x005d`, then dispatches every set bit. There is no
event-register write before or after dispatch. The status read is therefore
the acknowledgement/read-to-clear operation. Linux must not invent a W1C
write. A direct poll of `0x005b` consumes all pending event bits in that byte,
not only bit 1.

The last point limits the polling implementation. It is acceptable only in
the present tree, where `simple-mfd-i2c` supplies a regmap but no D2207 event
consumer and the J81 PMIC node has no Linux interrupt. J81 ADT does describe
the real PMU interrupt (`interrupt-parent` AP GPIO, `interrupts = <86 1>`), but
the meaning of the second cell has not been translated confidently to a Linux
trigger flag. Do not guess it for this measurement patch.

## Conversion formulas

| Quantity | Channel | Exact iOS 8.1 conversion | Linux units |
| --- | ---: | --- | --- |
| VBUS current | 9 | `floor(raw * 52800 / 1000)` mA | `raw * 52800` uA |
| VBUS voltage | 19 | `raw * 88` mV | `raw * 88000` uV |

The wrappers pass the `AppleDialogPMU` unity fixed-point multiplier `0x10000`,
so there is no further board multiplier in this path.

### Correction to earlier notes

`docs/plans/2026-09-26-tethered-tablet-and-charging.md` and
`research/2026-10-11-d2207-linux-vs-ios-charging.md` currently say channel 19
uses `floor(raw * 96192 / 1000)` mV. That is not what the exact J81 jump table
does. For channel 19, jump-table entry `0xffffff8002b494bc` targets
`0xffffff8002b49324`, which loads `0x157c0` (88000), multiplies the raw sample,
then uses the shared divide-by-1000 path. The result is exactly 88 mV/count.
The public iOS 10 implementation independently uses a direct multiply by 88.
The Linux patch should use 88000 uV/count.

## Smallest safe Linux patch

Extend the existing charger child rather than creating a new subsystem for the
first validation:

1. Add `struct mutex adc_lock` to `struct j81_d2207_charger` and initialize it
   in probe. Regmap's own lock covers individual transfers only; it cannot
   prevent a voltage read from starting in the middle of a current conversion.
2. Add one helper taking channel 9 or 19. Under the mutex:
   - read and save `0x0500`, `0x0501`, and `0x007b`;
   - read `0x005b` once to discard a stale completion;
   - clear `BIT(1)` in `0x007b` to match Apple's unmasking;
   - write `(saved_0500 & BIT(6)) | channel | BIT(7)` to `0x0500`;
   - poll `0x005b` for `BIT(1)`, sleeping about 1 ms, with a 1000 ms timeout;
   - immediately `regmap_bulk_read(..., 0x0502, result, 2)` and decode it;
   - restore the exact saved `0x0500`, `0x0501`, and `0x007b` values through a
     single cleanup path, including after timeout or any later error;
   - unlock and return the first operational error (or a cleanup error if the
     transaction itself succeeded).
3. Add `POWER_SUPPLY_PROP_CURRENT_NOW` and
   `POWER_SUPPLY_PROP_VOLTAGE_NOW` to `j81_d2207_properties`. On this USB-type
   supply they describe measured VBUS, matching existing Linux AC/USB supply
   practice. Return microamps and microvolts.
4. Have `power-diag` consume those two sysfs files. Do not add raw shell ADC
   writes.

Saving and restoring exact register bytes is more conservative in Linux than
copying Apple's broad `0x0501 &= 0x07` cleanup, because Linux did not establish
the boot-time state. The helper still saves/restores `0x0501` even though these
two channels do not modify it, making failure cleanup explicit.

Do not expose an arbitrary-channel userspace API yet. Do not add periodic
kernel sampling. One sysfs read should perform one bounded conversion.

## Uncertainties and limits

- The exact event vector and read acknowledgement are high confidence.
  Whether a masked ADC event still latches in `0x005b` is not established;
  the proposed helper mirrors Apple by temporarily unmasking it.
- Polling `0x005b` acknowledges every pending bit in that byte. This is safe
  only while Linux has no D2207 event controller/consumers. A real MFD IRQ
  driver must replace the poll before adding PMU event users.
- The J81 ADT identifies the PMU's AP GPIO interrupt as `<86 1>`, but Linux
  polarity/trigger translation is intentionally deferred.
- A mutex in the charger child cannot serialize out-of-band `i2ctransfer`
  writes or a future sibling ADC client. Operators must not run raw ADC writes;
  later move the lock/helper to a D2207 parent driver.
- `0x0500` bit 6 is preserved because Apple carries a cached control baseline;
  its full meaning is not named. Bits 5:0 are unambiguously the channel and
  bit 7 is start.

## One bounded hardware validation

After the coding agent implements and offline-tests the helper, perform one
boot and no policy changes:

1. With the existing 2400 mA input limit, read `current_now` and `voltage_now`
   once, then read them a second time. Log raw ADC bytes, decoded values,
   elapsed conversion time, and before/after `0x0500`, `0x0501`, `0x007b`.
2. Accept the mechanism only if both conversions complete without timeout,
   all three control bytes return to their original values, VBUS is plausible
   (roughly 4.4-5.5 V), current is plausible (0-3.3 A), and charging/USB stay
   present with no I2C, PMU or USB errors.
3. If the first conversion times out, stop. Capture `0x005b`, `0x007b` and the
   cleanup readback; do not increase current and do not loop conversions.
4. Only after the single reads pass, collect at most ten samples at one-second
   intervals alongside battery current/voltage, load, backlight and Wi-Fi.

That dataset can separate input power from system load without a USB power
meter. It is not a substitute for a meter's independent calibration, but it
is enough to test whether the 2400 mA ceiling is actually reached and whether
the battery is merely receiving the remainder after system consumption.


## Hardware validation, 2026-10-12 (T4 payload, user-approved; patch 0099 as built)

Bounded test on the booted iPad: control bytes read through a forced i2c read before and after each conversion, then voltage_now and current_now read twice.
- Mechanism: **works**. Every conversion completed (no timeout, no kernel error, USB and charging stayed up), and `0x0500`, `0x0501` and `0x007b` read `0x00`, `0x00`, `0xed` before, after every single conversion and at the end: the save/restore is exact.
- Magnitude: **the conversion factors in this note are wrong by a factor of 64**. voltage_now returned 311,608,000 uV and 311,696,000 uV (raw counts 3541 and 3542 at 88 mV/count = 311 V) and current_now 31,204,800 and 30,465,600 uA (raw counts 591 and 577 at 52.8 mA/count = 31 A). Both are impossible for a 5 V USB source, and a 12-bit sample cannot reach 311 V at any sensible full scale. Dividing by 64 (a 16.16-style fixed-point step, the wrappers pass a "unity" multiplier 0x10000) gives **4.87 V** and **~480 mA**, i.e. 1.375 mV/count and 0.825 mA/count, which put the 12-bit full scales at 5.6 V and 3.4 A (3.3 A is the reference maximum input current): plausible. Not yet confirmed from the Apple conversion routine; the acceptance criteria (VBUS 4.4-5.5 V, 0-3.3 A) failed with the documented factors, so per the plan the ten-sample run was NOT done.
- Next: confirm the /64 in the J81 conversion code (jump table at `0xffffff8002b494bc`/`0xffffff8002b49324`: is there a shift or a divide by 64000 rather than 1000?), then fix the factors in patch 0099 and re-measure once.
