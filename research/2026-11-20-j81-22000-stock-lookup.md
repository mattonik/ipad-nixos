# Stock lookup: what sets PMGR +0x22000 bit 31 (2026-11-20, offline)

Question: iPadOS reads +0x22000 = 0x80000000 before the GPC request; Linux (fresh boot, nothing written) reads 0x00000000 (`2026-11-20-j81-linux-pmgr-22000-result.md`). Who sets bit 31 on iPadOS, and what would a faithful Linux replay look like? Sources: the decompressed 19H394 kernel (sha256 c3507666...), and our iBoot/LLB images (12B410 and 15.8.8, decompiled/disassembled; `artifacts/live/private/{iboot-12B410,iboot-15.8.8,ghidra-iboot}`), plus the 2026-11-17 iPadOS ordinary-store captures.

## Findings
1. **iBoot and LLB write this exact word, and they clear bit 31.** Every one of the four images (iBoot 12B410, iBoot 15.8.8, LLB 12B410, LLB 15.8.8) has exactly one read-modify-write at physical 0x20e022000 (`mmio_*.txt`). Disassembly (iBoot 15.8.8 at 0x870015810, a six-instruction function; LLB 15.8.8 at 0x18039150c as the first step of its clock setup, followed by stores to the 0x20e02b0xx clock block): `x8 = 0x20e022000; w9 = *x8; w9 &= 0x7fffffff; *x8 = w9`. So the bootloader clears bit 31 of +0x22000 around its clock reprogramming. Linux boots checkm8 -> PongoOS -> m1n1 and never runs iBoot/LLB, and reads 0 there, so on the normal path bit 31 must be set again AFTER iBoot, by later software (the kernel) or by another iBoot step we have not decompiled, and iPadOS reads it set.
2. **No ordinary-store record at +0x22000.** The three 2026-11-17 iPadOS ordinary-store captures (93 records each, below the 96 overflow limit) contain no store at any 0x22xxx offset (the only 0x2xxxx offsets are +0x21000 and +0x21004 = 0x808). Window and region attribution of those rows is not fully known, so this is weak evidence that the kernel's ordinary PMGR writer does not store +0x22000 during that window.
3. **No direct immediate in the stock PMGR code.** In the 19H394 PMGR text range (0xfffffff006bb0000..0xfffffff006c92000, 231k instructions) there is no `add ..., #34, lsl #12`, no 0x22000 constant, and no `orr w, w, #0x80000000` that targets region 0 + 0x22000 directly. There are seven `orr #0x80000000` sites; two (0x6bcf164, 0x6bcf2dc) sit in clock-record helpers next to `setPLLOffMode` and write (via the generic register writer called as writer(this, offset, value, 0)) a field with bit 31 and then 0x40000000: record at `[this + 8976 + 24*idx]` (valid byte, two register-offset words at +4/+8 set by a setter at 0x6bbf784), index < 4. If that record table is where the kernel sets +0x22000 bit 31 with offsets coming from a table, the offset is data-driven and static immediate search cannot find it; the setter's callers are vtable calls (no direct `bl`). This is a hypothesis; I did not confirm it.
4. **Not in the ADT:** none of the pmgr node's properties carries 0x22000 as a word; +0x22000 is not one of the six `ps-regs` blocks (0x20000, 0x20100, 0x20200, 0x20300, 0x20400, 0x21000). The Linux words show a block of per-entry registers there (stride 0x10, many 0x80000000 and tuples such as 0x09040300 / 0x00120001 / 0x00080808 from +0x22090 on).

## Conclusion
The stock kernel setter of +0x22000 was not located; what is established: the bootloader clears the bit, iPadOS has it set before the GPC request, Linux (which skips the bootloader) has it clear while other 0x220xx words already carry bit 31 from earlier boot stages. A Linux replay would be `*(0x20e022000) |= 0x80000000` only if the word reads exactly 0 (readback must be 0x80000000), the same shape as the earlier guarded writers, but the meaning of the bit is unknown and the order relative to other stores is unconfirmed, so it needs a go-ahead.

## Cheap extra measurement prepared: iPadOS `p22`
Variants `p22` and `fender-p22` (`boot/make_j81_ios_state_probes.py`, read-only, disassembly checked, tests pass; decoder labels the fields) read the neighbouring words on iPadOS before and after GPC: +0x22004, +0x22008, +0x2200c, +0x22010 (before and after) and +0x22014 (after). Linux has +0x22004..0x2200c = 0, +0x22010 = 0x80000000. This shows whether only +0x22000 differs or the whole 4-word group, which decides whether the setter is a per-record enable of the form seen at 0x6bcf2dc.
