# J81 GPU voltage and the first working Linux identity recipe

**T1. Voltage mapping.** [Code] J81 12B410 iBoot reads the GFX table at physical 0x20e01c000, extracts bits 31:24, passes selector 2 and the byte to 0x87a0faa74, and publishes the return value in the DT at 0x87a0fd014. The thunk branches to 0x87a0eb24c. For selectors 0, 1 and 2 the routine returns 600 + floor(3125 × code / 1000) millivolts. The host test executed the original routine for all 256 codes at all three accepted selectors and one rejected selector. Thus 0x64 means **912 mV in Apple's published table**, from an unrounded nominal 912.5 mV. This establishes the legacy software conversion, not the voltage measured on 19H394 hardware. [Observed] In the working Linux recipe PMGR +2300c reads 0x164, and D2207 I2C0 address 0x3c row 0x0128 changes from 00 00 40 00 to 64 00 64 00. GFX code and PMIC bytes 0/2 agree. Bit 8 is outside the payload byte; its electrical/protocol function and the intervening DWI wire format remain unknown. The 0x28-spaced rows at 0100, 0128 and 01c8 correlate with CPU, GFX and SRAM respectively in earlier governor/GPC tests. The GPU buck identification is inferred, and neither byte is a calibrated output-voltage reading. Sources: packet dwion-core-result; research/2026-11-11-j81-dwi-voltage-transport.md; tools/test_j81_gfx_voltage.py.

**T2. DVFM.** [Capture + code] See perf-states.tsv. State 1 is the requested start state, 365 MHz nominal and code 0x64. State 5 shares that code and nominally runs at 182.5 MHz. States 1 and 5 tie for the lowest valid table voltage. State 0 has no valid PLL entry. There are four populated primary rows and four lower-frequency variants. The recorded companion bytes for states 1–8 are 70,70,70,80,70,70,70,80 in hex. Frequencies are table predictions, not clock measurements. 12B410 iBoot 0x87a0fcfdc..cffc decodes the feedback and dividers against 24 MHz. PMGR +1008 and +4008 are separate PLL1/4 startup controls; neither selects a GFX table index. The recipe requests GPC state 1; no explicit host store of 0x164 to the GFX VID register was shown. Sources: 20261108-perf-peek.log, research/2026-11-09-j81-gfx-perf-paired-capture.md, 2026-11-19-j81-page1-page4-clock-control.md, and runner identity plan/result.

**T3. Necessity.** [Observed] Two fresh DWI-on boots read revision 0x00070500, and the later identity run additionally read 0x011b0803 at +0x18 and zero at +0x24. Together these identify BVNC 7.5.8.3 on this J81. The upper 0x011b is unexplained. The DWI-off full-recipe attempts stalled. Older DWI-on attempts had different MiscACG/page-5 conditions. These controls support DWI as the missing condition in the tested recipe. They do not establish necessity of every other write. Firmware was not started, so firmware necessity and performance-only classifications remain open. See ablation.tsv. Sources: both November 22 request packets' context/notes and the November 21 no-core and bridge-readback results.

**T4. Early always-on.** [Observed] On this boot path Linux previously gated DWI around 0.7 seconds after handoff. A late DWI enable before GFX was sufficient for the successful runs. On stock DCE69446 the DWI driver's startup banner follows GPU revision by 21 ms; its MMIO initialization precedes the banner, so that banner cannot date each write. LLB and Linux have been observed to leave compatible block-level configuration in older builds; exact handoff on each successful run remains uncaptured. [Design] Validate the effective Linux DT has apple,always-on on ps_dwi (0x20e020120), verify domain state before userspace and at activation, then omit the late raw DWI store. Its old-value guard expects 0x200 and cannot validate a domain already on. Use the existing reference-held GFX activation and capture PMGR VID, PMIC row and identity; compare with the late-enable positive control. Sources: research/j81-hidden-state/{RESULT.md,boot-stages.md}, 2026-11-11-j81-dwi-measurements-review.md, runner summary.

**T5. Bounds.** [Observed/code] 0x7f is the largest GFX code in the captured valid rows (996 mV as reported by iBoot). 0x80 occurs in the separate companion field. Neither is a validated upper command limit. No board-qualified slew rate, fuse/temperature headroom, transient tolerance, per-rail clamp or safe PMIC override was established. The 256-code test measures a reporting function only. Use the existing stock state request for reproducing identity. A direct voltage write cannot be qualified from these results. Additional evidence needed: the D2207 rail definition and DWI transaction contract, per-unit limit/trim and ramp tables, and physical rail or characterized telemetry.

Adjust ARCHIVE to the mount name. Compare stdout with perf-states.tsv. The reporting arithmetic is proven for the extracted 12B410 code; the exact 19H394 transport implementation and physical calibration are open.

Keep DWI on, single activation, identical mappings and the existing 20 s watchdog and breadcrumbs.
