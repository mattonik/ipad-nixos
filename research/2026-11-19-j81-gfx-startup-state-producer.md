# Who sets the GFX startup state on J81?

**A fresh ApplePMGR object starts with GFX at zero. The stock 19H394 device-tree initializer leaves that byte alone for GFX.** On the startup branch that scans the power-state banks, zero therefore predicts a skipped forward pass and a reverse setter request of zero, unless an intervening writer changed it. The successful November 14 core read has no measurement of that byte. A different boot does identify a writer of 15 during the later AGX clock-provider request. These results shift the early-boot question to whether a request intervened, or whether the recipe worked with GFX still at zero. ## Follow the byte from allocation to replay

Addresses below are virtual-address suffixes after `0xfffffff00` for J81AP build 19H394. Object offsets are relative to the PMGR instance in memory.

| Stage | Exact-build evidence |
| --- | --- |
| Allocation | `6c89f40..6c89f48` requests 0x35078 bytes. The stub resolves to `_OSObject_typed_operator_new` at `7689d00`. Its allocation paths carry flag 0x4, including the `zalloc_flags` call at `7689d54`. The constructor installs the T7001 vtable at `6c89f68`. The reviewed constructor copies do not cover +0x19110. XNU defines 0x4 as zero-filled allocation. [Apple allocator flags](https://github.com/apple-oss-distributions/xnu/blob/xnu-8019.41.5/osfmk/kern/zalloc.h#L319-L345) |
| Identify GFX | The stock 48-byte PMGR record gives ID 0x7c, bank 3, enabled lane 4. Record bytes +0, +2 and +0xf are zero. All 98 records use the byte-ID layout. The +4 parent list ends at its first zero. GFX has no parents, and no other record names GFX as a parent. |
| Sample a physical lane | In the ordinary physical-row path, `6bc2a00` calls `6bc6c20`. Slot +0x980 maps to `6bd0478`; it reads the 32-bit lane word. `6bc6c9c` keeps bits 3:0 and `6bc2a04` compares with 15. For GFX this is region 0 +0x20320. Bits 3:0 are TARGET, and ACTUAL is bits 7:4. [Pinned Linux driver](https://github.com/HoolockLinux/linux/blob/6831bc701a6ce059e71e5aaa9488c9195bea6927/drivers/pmdomain/apple/pmgr-pwrstate.c) |
| Decide whether to seed | For this row the condition at `6bc2a68..6bc2a80` is **record[0] bit 0 AND (sampled target == 15 OR selector-1 debug match)**. A match can request state 15 from the hardware at `6bc2a60`. Even then, the following bit-0 check skips the software seed for GFX. For instance 0, the would-be bit is mask 0x10000000 at +0x18ab0, in the bitmap based at +0x18aa4. |
| Consume the seed | `6bc3bac..6bc3bd4` tests each ID. A set bit calls the aggregate builder with new=15, old=0, null transition list and null count. It then writes the separate client cache at +0x19554+ID. A clear bit skips both. For GFX the client-cache offset is +0x195d0. |
| Write the aggregate | `6bc8e48..6bc8e64` computes and saves the address **this + 0x19094 + instance × 0x260 + ID**. For GFX instance 0 that gives +0x19110. `6bc9114` compares the effective request with the old aggregate. If they differ, `6bc924c` stores the new byte. Only after that does it test whether to append a transition to a caller's list. |
| Read it during startup | On the `this+0xe4 == 0` path, `6bcd464..6bcd46c` reads this byte and checks for 15. A 15 selects the forward active path. A zero skips it and reaches the reverse setter at `6bcd558` with 0. The setter can short-circuit, so the absence of an MMIO store cannot identify the branch. |

## Account for the other writers

A scan of every aligned direct B/BL in the digest-checked prelinked executable segment finds four sites targeting the aggregate builder at `6bc8de4`. The first is the initializer above. The second, `6bc9210`, propagates a transition to a device's parents. No stock tree edge propagates to GFX. The third, `6bd0434`, takes IDs from a separate bitmap at +0x19a14. Its per-row producer at `6bc2774..6bc2788` needs record[0xf] bit 4, also clear for GFX. Its execution before replay has not been established. This accounts for the direct branches in that segment. An indirect caller or a separate memory copy would require additional evidence.

The fourth site, `6bd7c18`, is the generic provider callback. After a changed GFX request, `6bd7bd8` stores the client value and `6bd7c18` calls the builder with a transition list. GFX bypasses the parent reference counters. A direct request of 15 can then reach `6bc924c`. A changed request can also be promoted to 15 by record[0] bit 3 (clear here), the `light-em-up` flag parsed into +0x145, or a matching packed ID in `pmgr-debug-always-on` at +0x130. These options change an effective request once the builder runs. No earlier GFX invocation is established on the successful manual-recipe boot.

## Offline tests and retained evidence

The [host audit](../tools/audit_j81_pmgr_start.py) checks the kernel and tree digests, machine words for the two seed gates, direct branch sites, aggregate store, replay comparison, and J81 device topology. A separate native ARM64 fixture exercised the stock low-nibble mask, comparison, conditional result and two seed branches over 4 flag values × 256 synthetic register bytes × 2 supplied debug-match results. All 2,048 cases matched the condition above. The fixture supplied the sample and match and performed no MMIO.

The November 14 20:57 archive contains five recipe markers in one boot. It records initial PS=0x300, GPC completion in 0x3929 ticks, three page-5 samples with bit 30 set, and CORE=0x00070500. The initial PS word supplies target=0 and actual=0 at the recipe boundary. The markers carry neither the earlier software byte nor a setter caller. The archive also retains messages from other boots. In particular, the November 10 matrix and dispatcher exports contain a changed GFX aggregate, 0→15; the dispatcher export identifies ID 0x7c and a one-entry transition list. Assigning those older rows to the November 14 boot would create a false pre-start writer. ## Next decision

Keep the early successful recipe as the control. If a retained boot-scoped record shows a pre-replay GFX transition, identify the writer's caller, old and effective values and its order relative to the replay check. A recorded zero at the check or a GFX reverse setter with argument zero supports the fresh-object prediction. A forward replay caller establishes 15 at the check even if the first writer is missing. If the archive has only the five recipe markers, leave the software byte unknown and prioritize the existing Linux setter observer and page-5/GPC comparison. The current evidence gives no reason to force the Linux domain always on. [Build-agent instructions](j81-gpu-builder-handoff.md#identify-the-gfx-startup-writer)
