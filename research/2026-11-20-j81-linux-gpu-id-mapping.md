# Linux mapping used for the November 19 J81 timed GPU-ID attempt

The timed reader opens /dev/mem with O_RDWR | O_SYNC and requests one read-only shared page at 0x201000000 before issuing the GPC sequence. It checks the return values of all three mmap calls before proceeding. After the poll it reads page 5 and logs a counter delta, then loads the volatile 32-bit word at byte offset 0x20 and executes DSB LD. The saved 0x40000000 page-5 value and subsequent checkpoint put this boot beyond the mmap error paths. The next missing message localizes the failure to an interval that includes the load and barrier. The log alone cannot distinguish the instruction at which progress stopped. The source is the mailbox's November 19 linux-timed-core-prepared/gpu-gpc-timed-core.c, lines 75–108. [Boot evidence](2026-11-19-j81-page5-high-core-stall.md)

## From mmap to memory type

1. mmap_mem_prepare verifies the physical range and policy, then calls phys_mem_access_prot and installs the full PFN remap. On this 4 KiB kernel offset 0x201000000 selects PFN 0x201000. The kernel receives the physical page address as the mmap byte offset. [Pinned memory driver](https://github.com/HoolockLinux/linux/blob/6831bc701a6ce059e71e5aaa9488c9195bea6927/drivers/char/mem.c#L325-L362)
2. arm64 phys_mem_access_prot tests pfn_is_map_memory first. A false result selects pgprot_noncached regardless of the file's O_SYNC flag. With mapped RAM, O_SYNC selects pgprot_writecombine. The PFN test checks address representability and memblock_is_map_memory. [arm64 protection selection](https://github.com/HoolockLinux/linux/blob/6831bc701a6ce059e71e5aaa9488c9195bea6927/arch/arm64/mm/mmu.c#L96-L105) · [PFN classification](https://github.com/HoolockLinux/linux/blob/6831bc701a6ce059e71e5aaa9488c9195bea6927/arch/arm64/mm/init.c#L167-L177)
3. pgprot_noncached selects MT_DEVICE_nGnRnE (index 3) with execute-never flags. pgprot_writecombine selects MT_NORMAL_NC. Ordinary pgprot_device selects MT_DEVICE_nGnRE, so substituting default kernel ioremap may change the type as well as the exception level. The difference between nGnRnE and nGnRE concerns early acknowledgement of writes. A difference in that bit alone gives no direct explanation for an isolated read stalling. [Protection macros](https://github.com/HoolockLinux/linux/blob/6831bc701a6ce059e71e5aaa9488c9195bea6927/arch/arm64/include/asm/pgtable.h#L752-L762) · [MAIR indices](https://github.com/HoolockLinux/linux/blob/6831bc701a6ce059e71e5aaa9488c9195bea6927/arch/arm64/include/asm/memory.h#L170-L178)

The earlier J81 runtime FDT and /proc/iomem put 0x201000000 outside both System RAM ranges. Together with the source this supports **Device-nGnRnE** for the timed boot. Its own PTE, MAIR and memblock table were not captured. Read-only userspace permission, EL0, the barrier after the load, and mapping time are separate comparison axes. A host build can verify instruction width and order but cannot establish transaction completion or a live PTE. [November 7 memory evidence](2026-11-07-j81-weekend-readonly-capture.md)

For a stronger Linux check, first look for the exact timed image's config, build provenance, and boot-specific memory-range records. A later Linux-only page-table observation could map the page and report its PA/AttrIndx and selected MAIR byte without accessing GPU-ID. Map creation or a matching descriptor alone cannot test downstream power/reset state.

## When Linux installs the entry

For a newly allocated VMA, __mmap_region calls mmap_action_complete before returning its address. MMAP_REMAP_PFN invokes remap_pfn_range_complete. The page-table walker installs a special PTE from the requested PFN and protection using set_pte_at. This timed reader is a fresh process mapping three disjoint physical ranges. Successful mmap therefore predicts a populated core PTE before the GPC batch. A first-load TLB miss and hardware page-table walk remain possible. Installing this descriptor does not issue a GPU register read. [mmap completion](https://github.com/HoolockLinux/linux/blob/6831bc701a6ce059e71e5aaa9488c9195bea6927/mm/vma.c#L2885-L2898) · [Action dispatch](https://github.com/HoolockLinux/linux/blob/6831bc701a6ce059e71e5aaa9488c9195bea6927/mm/util.c#L1478-L1496) · [PFN completion](https://github.com/HoolockLinux/linux/blob/6831bc701a6ce059e71e5aaa9488c9195bea6927/mm/memory.c#L3346-L3356) · [PTE installation](https://github.com/HoolockLinux/linux/blob/6831bc701a6ce059e71e5aaa9488c9195bea6927/mm/memory.c#L3042-L3068)

The pinned CPU setup constructs MAIR_EL1_SET with MT_DEVICE_nGnRnE at index 3, encoded as byte 0x00 in bits 31:24. It loads that value at proc.S:507 and installs it with MSR MAIR_EL1 at line 546. This is independent of the GPU's power state. The standard arm64 debugfs kernel_page_tables walker uses init_mm, so that dump alone would not report the reader's userspace PTE.
