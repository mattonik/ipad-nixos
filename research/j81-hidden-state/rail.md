## GFX voltage and external PMU

[Read from code] Before the end-of-start hook, exact 19H394 PMGR calls instance slot +0x698 with enable=1 at VA suffix 6bcd100. The J81 target is 6c8a164. Disassembling through 6c8a234 gives three ordered writes on this branch, all to ordinary PMGR region 0. At 6c8a1ac request PA 0x20e023000 = old & 0xfffff0ff. At 6c8a1f0 write PA 0x20e023010 with the high byte of the 64-bit CPU-cluster table word at 0x202220068 + 8*state, state = (cluster[+0x20] >> 22) & 7. At the 6c8a234 tail write PA 0x20e023004 with (cluster[+0x110] >> (8*state)) & 0xff. The disable arm instead sets bits 11:8 in the control. The method does not write 0x20e02300c, send a PMIC bus command, or read any PMIC response. A later 0x170 SRAM readback is not itself the byte that this method requested. Source: 19H394 kernel c3507666… and research/2026-11-19-j81-pmgr-start-resources.md.

[Board data] Exact J81 arm-io/dwi (dwi,t7001) covers PA 0x20e200000..0x20e200fff, clock-gates 0x36. PS word PA 0x20e020120 is separate from ps_gfx. arm-io/i2c0/pmu names pmu,d2207 with first reg cell 0x3c. The tree gives the host's I2C attachment, not the bus waveform or destination rail for a GPC request. A case-insensitive search of property values found no VDD_GPU, VDD_GFX, VDDGPU or VDDGFX labels. No PMU node property name identified an ADC, regulator or power-good readback for the GFX rail. No GPU-specific PMIC SPI/SPMI/SMC call was identified on the decoded PMGR voltage method or native pre-ID clock/power/Fender path. Independent kernel service start order remains unmeasured.

[Observed in separate captures] iPadOS and Linux reported 0 → 0x164 at PA 0x20e02300c around the GPC request. Linux DWI-on tests sampled D2207 row 0x0128 bytes 0/2 changing 00/40 → 64/64 and DWI config +0/+4 values 1/0x3c. An early continuous DWI hold and a 20-domain restoration did not yield an observed ID; on the latter, the subsequent core access stalled. The historical runs had page 5 clear. On newer Linux runs page 5 rises and core still stalls; the latest packet supplies no same-boot external PMU byte trace. See research/2026-11-11-j81-dwi-voltage-transport.md, especially its November 15 follow-up, and research/2026-11-11-j81-dwi-measurements-review.md. The N61 GPU result is a different board.

[Inference] The state-1 GFX perf table first word 0x6436d063 exposes code 0x64 and the PMU change is consistent with delivery of a digital request. The destination buck identity, voltage at the GPU pins, regulator enable/ramp, and isolated core/fabric rail are unmeasured. The software explanation "Linux never delivers the code" already conflicts with the older Linux captures. No target/command/value for a new regulator write follows. An analog or isolation difference remains possible but unranked by direct voltage evidence.

[Phase and measurement] Separate PMGR initialization from the observer's later GPC-triggered rail-code transition. For matched before/after GPC phases compare 0x20e02300c, DWI PS, and optionally the two known DWI config words, ideally with existing diagnostic captures. To test the external part, use a supported PMIC diagnostic with ownership of its bus to sample the previously documented 0x0128 bytes on each OS and record phase, boot and access width. A print-only MMIO observer cannot read an I2C register by treating 0x0128 as an MMIO address. Equality would compare digital codes only; physical voltage requires an identified telemetry channel or calibrated board measurement. Full PMU dumps have previously cleared events. No voltage/clock/reset write or repeat core read is required to perform this comparison.

[Code] PMGR perf-regs initializer at 6bc0214 consumes J81 index 0, offset 0x28000; perf-domains at 6bc0a98 covers SOC and CPU only, SOC voltage-states0 zero-filled. SGX gfx-qos has two LE32 ones, with no literal consumer identified in the matching image. SGX function-clpc_enabled resolves to a query writing the boolean pmgr field +0x1a0 != 0 to caller memory (6bddd7c); it is not a PMIC command. SGX CLPC feedback and subsequent firmware DVFM have no demonstrated pre-hook GFX rail action. 0x20e01c200 GFX perf readbacks around GPC do not imply a CPU-issued write there. Sources: research/2026-11-14-j81-ios-voltage-manager-enable.md, second and third pass; research/2026-11-18-j81-gfx-state-word-comparison.md.

### Matching the PMIC driver's actual start function

[Read from code] Exact 19H394 prelink personality PMU selects AppleD2207PMU on AppleARMIICDevice with IONameMatch pmu,d2207, matching the J81 i2c0/pmu node. Its constructor at 0xfffffff006ce7044..704c installs address point 0xfffffff007000920. Entry +0x2b0 is 0xfffffff006ce71f0, the start implementation. It calls the superclass at 6ce7224, tests its return, and later logs the class-specific start string at 6ce7290. Normal returns share an epilogue ending 6ce7b98. The inspected AppleD2207PMU function has real external-register operations: for example 6ce771c..7744 reads PMIC 0x444 then requests old | 0xf and 6ce7748..7788 reads PMIC 0x11 then requests old | 1. Read/write virtuals +0x5c8/+0x5d0 resolve to 6ce4b1c/6ce4898 in com.apple.driver.AppleDialogPMU. These addresses are PMIC register numbers, not SoC MMIO. No GPU-specific meaning for these two bytes was found.

[Read from code and tree] Importantly, the literal “using DWI for BUCK changes” is conditional. At 6ce7790..77b0 the driver looks up provider property dwi-buck-control, checks its object type, and skips the block if absent. The taken path logs the string at 6ce77c0, reads the property's first word, and saves it in software field +0x1dc at 6ce77d8. That branch itself issues no PMIC command. The property appears nowhere in the exact J81 ADT. Runtime injection remains possible. This is independent of hardware transport activity inferred from DWI-on Linux measurements.

[Observed and code] On boot DCE69446 the start message at 6ce7290 was logged 72.306 ms after the successful early revision record. The listed writes at 6ce771c and later therefore occurred too late in this invocation to explain that read. The superclass call at 6ce7224 precedes the message. Its work, PMIC state inherited from firmware, and activity on other threads require separate attribution. See RESULT.md.
