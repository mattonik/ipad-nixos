## Why this is next

Per `docs/project-status.md` and `docs/plans/2026-09-08-ipad-air2-driver-bringup.md`'s
"Priority review" (2026-09-08 overnight): touch is the highest-value next
subsystem because Linux already has the protocol/input driver
(`drivers/input/touchscreen/apple_z2.c`, used today for Mac Touch Bars) and
the real J81 ADT already confirms every resource this needs -- unlike Wi-Fi,
which needs a much bigger T7000 PCIe host port before anything can probe at
all.

## Split into stages

Mirroring the BT-1/2/3 and BAT-1/2/3 pattern already proven twice this
session: prove the controller transport first, independent of the actual
peripheral, before adding anything touch-specific.

- **TOUCH-1** (this document's current focus): port/clean the S5L8960X SPI
  controller support into the pinned kernel's `drivers/spi/spi-apple.c`, add
  the SPI3 DTS node + PMGR power domain + CS pinmux, and get a stable
  `/sys/class/spi_master/` entry. No touch driver binding yet.
- **TOUCH-2**: add the J81 touch child node and the smallest `apple_z2` DT
  match needed to observe a reset/IRQ sequence and the exact firmware
  request. The child `reg` encoding and PMGR clock arguments still need more
  ADT/driver decode work -- see "Open research" below.
- **TOUCH-3**: firmware extraction (local IPSW, kept outside Git, matching
  this project's established firmware-handling discipline) and calibration
  wiring, plus the now-identified D2207 LDO14 and AP GPIO95 power sequence.
  Live reads show the analog rail is off, so TOUCH-3 must own this sequence.

## Evidence: independently re-verified against the real J81 ADT, not just trusted from prior docs

Both `docs/project-status.md` and the bring-up plan's "Priority review"
section already stated resource numbers for touch. Before writing any code
against them, re-decoded them directly from the private raw capture
(`artifacts/adt/20260908T082112Z-j81.adt`, git-ignored) the same way BT-1's
UART3 numbers were verified -- every value below is byte-exact confirmed,
not copied from the summary docs.

### SPI3 controller node

```
compatible                       spi-1,samsung
function-spi_cs0                 1f 00 00 00 4f 49 50 47  33 00 00 00 01 00 01 00
interrupt-parent                 0x00000018
interrupts                       0x0000009b
clock-gates                      0x0000004d
reg                              00 c0 08 0a 00 00 00 00  00 40 00 00 00 00 00 00
```

- `interrupts = 0x9b` = 155 (AIC hardware IRQ).
- `clock-gates = 0x4d` = 77.
- `reg`'s first 8 bytes decode (little-endian) to `0x0a08c000`; combined
  with this SoC's established high-cell convention (same one UART3/UART5
  use: DTS address `<0x2 0x0a0cc000 ...>` for the ADT's raw `0x0a0cc000`),
  the real DTS address is `0x20a08c000`. Second 8 bytes decode to size
  `0x4000` -- the same 16 KiB register-window size as every other UART/SPI
  peripheral on this SoC so far.
- `function-spi_cs0`: phandle `0x1f` (the AP GPIO controller -- same
  phandle BT-1/BAT-3's pin decodes used), `"OIPG"` magic, args
  `[0x33, 0x10001]`. Resource number `0x33` = **51** = AP GPIO51, matching
  `docs/project-status.md`'s claim exactly.
- `compatible = "spi-1,samsung"` matches the naming convention already
  established for UART (`uart-1,samsung` -> Linux `apple,s5l-uart`) --
  strong, independent confirmation that this is the same "Samsung IP
  block" family on the Linux side, not a guess.

### Touch child node (`multi-touch`)

```
compatible                       multi-touch,j82
function-display_sync            1f 00 00 00 4f 49 50 47  37 00 00 00 01 01 00 02
interrupt-parent                 0x0000001f
interrupts                       54 00 00 00 00 00 00 00
function-power_ana               4e 00 00 00 4c 75 6d 70  0e 02 00 00
function-power_ldo               1f 00 00 00 4f 49 50 47  5f 00 00 00 01 01 00 00
function-reset                   1f 00 00 00 4f 49 50 47  52 00 00 00 01 00 01 00
function-enable_cs               1f 00 00 00 4f 49 50 47  33 00 00 00 01 01 00 00
function-clock_enable             1a 00 00 00 4b 4c 43 54  08 00 00 00 64 00 00 00 00 80 00 00
reg                               00 00 00 00 7c 00 00 00  00 00 01 08 88 13 00 00 10 27 00 00 ...
multi-touch-calibration          [not reproduced -- real per-device calibration blob + what
                                   appears to be a part/serial-like string; read during
                                   decode, intentionally not copied anywhere, per this
                                   project's standing rule against committing calibration
                                   or per-device data]
```

- `function-display_sync`: phandle `0x1f`, args `[0x37, 0x02000101]`.
  Resource `0x37` = **55** = AP GPIO55, matching the doc's "display sync
  GPIO55" claim.
- `interrupts = 0x54` = **84**, with `interrupt-parent = 0x1f` (the AP GPIO
  controller itself, *not* AIC) -- this independently confirms something
  the summary docs stated but didn't make explicit: touch's own IRQ is a
  **GPIO interrupt** (AP GPIO84 configured as an edge interrupt), a
  genuinely different mechanism from SPI3's own AIC-routed controller
  interrupt above. Worth keeping straight when writing TOUCH-2's DTS: this
  is `interrupts-extended` on the GPIO controller, not another AIC entry.
- `function-power_ldo`: phandle `0x1f`, args `[0x5f, 0x101]`. Resource
  `0x5f` = **95** = AP GPIO95, matching "LDO GPIO95".
- `function-reset`: phandle `0x1f`, args `[0x52, 0x10001]`. Resource
  `0x52` = **82** = AP GPIO82, matching "reset GPIO82".
- `function-enable_cs`: phandle `0x1f`, args `[0x33, 0x101]`. Resource
  `0x33` = **51** -- the *same* AP GPIO51 the SPI3 controller node itself
  already names as `function-spi_cs0`. Self-consistent, not a new pin.
- `function-power_ana`: phandle `0x4e` -- the **same phandle BT-3 already
  identified as the `pmu,d2207` node** -- but a completely different magic,
  `"Lump"` (`4c 75 6d 70`) instead of the `"OIPG"` GPIO-function format
  used everywhere else so far, with only one trailing arg word:
  `0x0000020e` = `0x20e`. The Apple D2207 LDO function now decodes this as
  zero-based LDO index 14 with enable-only flags; see the dated result below.
- `function-clock_enable`: phandle `0x1a` resolves to J81's `pmgr` node. Its
  `"KLCT"` magic (`4b 4c 43 54`) and args `[8, 0x64, 0x8000]` describe a
  PMGR clock operation, but the three fields still need exact decoding.
- `reg`: a 32-byte value, clearly *not* a simple memory address (SPI3's own
  child addressing is `#address-cells=1`/`#size-cells=7` on the parent --
  an unusual shape suggesting Apple's SPI-child ADT convention packs
  multiple numeric fields, not just a chip-select index). Not decoded yet
  -- this is exactly the kind of thing that must be understood correctly
  before TOUCH-2's DTS child node can be written with real values instead
  of guesses.

## Pinmux alt-function: resolved, hardware-confirmed 2026-09-12

`function-spi_cs0`'s flags word low byte is `0x01`, while most UART records use
`0x02`. An initial survey treated that byte as the Apple pinmux selector:

```
function-tx   flags low byte: 0x02, 0x01, 0x02, 0x02, 0x02, 0x02, 0x02, 0x02
function-rts   flags low byte: 0x01, 0x02, 0x02
```

BAT-4 disproved that interpretation. GPIO34's UART5/HDQ record carries `0x102`,
but the pad works only on Apple peripheral function 1. The flags still vary
and may describe resource semantics, but they are not a direct pinmux index.
`APPLE_PINMUX(51, 1)` was therefore built as a provisional value. **No A/B
test ended up being needed**: TOUCH-1's hardware gate found the SPI3
controller genuinely probing, and reading live pinctrl debugfs during that
same session directly confirmed
`pin 51 (PIN51): device 20a08c000.spi function periph1 group PIN51` --
function 1 is correct, hardware-confirmed, not just asserted in the DTB. See
the TOUCH-1 hardware-gate section below for the full evidence.

## Power-resource result, 2026-09-10

The `"Lump"` blocker is resolved from the iOS 10.3 s8000 Apple D2207 and
multitouch drivers, with a live read-only cross-check:

- `0x20e` encodes zero-based LDO index 14 (called LDO15 in Apple's one-based
  logs) and flags `0x02`, an enable-only operation that preserves the
  programmed voltage.
- D2207's LDO14 descriptor uses a 5,000 mV minimum, 50 mV steps, voltage
  register `0x0398` with mask `0x1f`, and enable register `0x0084` bit 2.
- Live J81 values are `0x0398 = 0x14`, which decodes to 6,000 mV, and
  `0x0084 = 0x00`, so the analog touch rail is currently disabled.
- SPI3 and touch GPIOs 51, 55, 82, 84 and 95 are unclaimed in the current
  Linux session, consistent with the touch patches remaining outside the
  active payload.
- Apple's multitouch power-on order is the PMU analog rail, optional delay,
  then AP GPIO95. Power-off reverses those two controls. J81 has no optional
  Mamba stage and no analog-delay property, so its minimum sequence is D2207
  LDO14 on, then GPIO95 on; GPIO95 off, then LDO14 off.
- The same Apple driver identifies the J82/J81-family personality as
  `multi-touch,j82` with a 15 ms reset-deassert delay, parser type 1,
  parser-options 16, touch-size ID 3, and firmware merge name `C1F15,2`.

The `"KLCT"` provider is also identified: ADT phandle `0x1a` is `pmgr`.
The exact meaning of `[8, 0x64, 0x8000]` remains unresolved, so it is not yet
safe to replace that callback with a raw PMGR write.

## Open research (blocks TOUCH-2, does not block TOUCH-1)

Updated 2026-09-10 after reading the mainline binding and driver directly.
One of the two blockers is substantially resolved; the other is narrowed.

### Resolved: the child `reg` does not need Apple's packing decoded

The parent `spi3` node carries `#address-cells = 1` and `#size-cells = 7`,
so the child's 32-byte `reg` parses as one address cell followed by seven
size cells:

```
address:  0x00000000
sizes:    0x0000007c  0x08010000  0x00001388  0x00002710  0x0  0x0  0x0
```

The address cell is the SPI chip select, and it is **0**. That is the only
part Linux consumes: `apple,z2-multitouch.yaml` pulls in
`/schemas/spi/spi-peripheral-props.yaml#` and its own example writes
`touchscreen@0 { reg = <0>; ... }`. The remaining seven cells are Apple's own
packed parameters, read by Apple's driver, not by Linux. **TOUCH-2's DTS
child can therefore be written with `reg = <0>` and standard properties, with
no further decoding of that blob.**

Two of those cells (`0x1388` = 5000 and `0x2710` = 10000) are plausible
candidates for the touch coordinate-space dimensions that the binding
requires as `touchscreen-size-x`/`touchscreen-size-y` -- but that is a
*guess from shape alone*, not evidence, and must be confirmed against
Apple's driver or live data before being written into a DTS.

### Narrowed: `"KLCT"`

Still undecoded, but better scoped. The `spi3` *controller* node already
carries its own `clock-gates = 0x4d` and `clock-ids = 0x12e`, while
`function-clock_enable` sits on the *child*. The child's KLCT resource is
therefore not simply the SPI3 gate restated, and enabling SPI3 does not
implicitly cover it. Provider is PMGR (phandle `0x1a`); Apple's driver calls
it with 3 to enable and 0 to disable; args are `[8, 0x64, 0x8000]`.

Checked the ADT `pmgr` node itself (2026-09-10) hoping the three words would
index something visible there -- they do not; it is the large SoC
power-manager node (voltage states, bridge settings, perf regs) with no
clock table those args obviously select into. **Concrete next action, not
"needs decoding":** the `Lump` format was resolved by reading Apple's own
D2207 and multitouch drivers, and it is the *multitouch* driver that also
makes this `clock_enable` call -- so the same
`AppleMultitouchSPI`/`AppleMultitouchSPIJ82` kext already used for that win
is where to look, specifically its clock-enable path, rather than trying to
infer the layout from the ADT alone.

Deliberately not guessed at: `0x8000` = 32768 invites a "32.768 kHz
reference clock" reading, and `0x64` = 100 could be a clock index, but
neither is evidence and this project has already been bitten once (BAT-4) by
treating a plausible-looking ADT field as a known encoding.

### KLCT, 2026-09-12: local kext copies checked, both dead ends

Went looking on this Mac for the `AppleMultitouchSPI`/`AppleD2207PMU` copies
this document says were "already used" for the `Lump` decode, specifically
to read their clock-enable path. Found two real candidates and ruled both
out directly rather than assume either would help:

- `/System/Library/Extensions/AppleD2207PMU.kext` (this host's own, native)
  is metadata only -- `Info.plist`/`version.plist` and a code-signature, no
  executable. Modern macOS collapses built-in kext code into a single sealed
  kernelcache; the standalone binary this document's earlier decode presumably
  read is not something that persists on disk here, matching this project's
  own discipline of not keeping extracted proprietary binaries around.
- The only real `AppleMultitouchSPI`-family executable found anywhere on
  this machine is `MultitouchHID` inside Xcode's cached iOS DeviceSupport
  symbols, for **iPhone18,1 running iOS 26.5.1** -- more than a decade newer
  than J81/J82. Personality/quirk code for a discontinued 2014 board is very
  unlikely to survive in a build that current; not disassembled, on the
  reasoning that the ratio of "chance of a real answer" to "time spent" is
  poor without confirming it retains anything relevant first.
- Confirmed on live hardware (same booted TOUCH-1 session, purely read-only)
  that Linux's own frameworks don't already model this resource under a
  different name: `/sys/kernel/debug/clk` only has `clkref`, and
  `pm_genpd_summary` shows the expected, unrelated `spi3 off-0` /
  `20a08c000.spi suspended` runtime-PM state -- normal idle behavior, not a
  KLCT-shaped entry anywhere. There is nothing already exposed to read.

**Where this actually needs to go next:** a fresh IPSW-extracted copy of an
*older* iOS build (a version that still ships J81/J82 personality code) is
the real next step, not a shortcut available from what's already on this
machine. That is real, scoped work -- extract locally, keep the binary out
of Git per this project's existing firmware-handling rule, disassemble the
multitouch driver's clock-enable call site -- not something to rush through
today.

### TOUCH-3, 2026-09-13: substantial progress, no IPSW download needed at all

This document's own "Primary references" section already linked a public
repo of unstripped Apple driver kexts
([userlandkernel/ios-unstripped-kexts](https://github.com/userlandkernel/ios-unstripped-kexts),
iOS 10.3, s8000) as the source used for the `Lump` decode. Re-fetching it
(a sparse `git clone`, a few MB total, not a multi-GB IPSW) and reading
further into it resolved most of what a full IPSW extraction was assumed
to require. Nothing here touched real J81 hardware; this is all static
analysis of Apple's own compiled binaries, kept locally and out of Git per
this project's existing firmware-handling rule.

**Solid: the touch ASIC's own bring-up registers, straight from
`AppleMultitouchSPIJ82.kext`'s `Info.plist`** (`IONameMatch:
multi-touch,j82`, the exact ADT compatible this board's touch node uses --
confirmed the personality really is shared between J81 and J82, not
guessed):

| Key | Value (decimal → hex) | What it is |
| --- | --- | --- |
| `clk32-clock-enable-addr` / `-val` | `268449048` / `1` → `0x10003518` / `1` | Enables the touch ASIC's own 32.768 kHz reference clock |
| `fll-mval-addr` / `fll-mval` | `268447840` / `6068` → `0x10003060` / `0x17b4` | FLL multiplier register + value for clock generation |
| `fw-execute-addr` | `268448768` → `0x10003400` | Poke this to make the touch ASIC jump into loaded firmware |
| `cal-dl-addr` / `prox-cal-addr` | `268472320` / `268473856` → `0x10009000` / `0x10009600` | Calibration blob download addresses |
| `reset-deassert-delay`, `touch-size-id`, `parser-type`/`-options`, `mt-merge-personality` | `15`, `3`, `1`/`16`, `"C1F15,2"` | All independently reconfirm the personality values already noted above -- same source, second read |

These addresses are all inside the touch controller's *own* internal
address space (0x1000_3000-0x1000_9600, far too small a range to be an AP
physical address) -- reached over the Z2 SPI protocol as read/writes into
the chip's own memory, not `ioremap()`-style host MMIO. This is a
genuinely new, concrete, high-confidence result: enough to implement most
of the touch bring-up sequence (enable clk32, set the FLL multiplier,
download firmware, kick `fw-execute`, then calibration) without touching
KLCT at all for these specific steps.

**Partial: KLCT's actual mechanism, traced by disassembling the real
handler class.** The binary literally contains the string
`function-clock_enable`, confirming
`ApplePMGRFunctionClockGate::callFunction` (in `ApplePMGR.kext`, the
generic base PMGR driver also in this same repo) is the real handler.
Disassembled with Xcode's bundled `llvm-objdump` (no IDA/Hopper needed):

```
ApplePMGRFunctionClockGate::callFunction(this, param1, param2, param3):
    x0 = this->offset_0x28          ; set during init via safeMetaCast
    bl  ApplePMGR::_enableDevice(x0, param1)
    return 0
```

`this->offset_0x28` is populated in `initWithTargetDataAndSymbol()` by a
`safeMetaCast` of a field set by the (unseen, base-class) constructor that
parses the raw `OSData` -- i.e. our own ADT's exact
`function-clock_enable = [8, 0x64, 0x8000]` bytes -- into a registered
per-device object. `_enableDevice` → `_enableDeviceGated` →
`_updateDeviceStatus` is a reference-counted enable/disable tracker
indexed by that same device value, confirmed by reading its actual
disassembly (not assumed from the name).

**Cross-validated against the real J81 ADT** (`artifacts/adt/20260908T082112Z-j81.adt`,
private, git-ignored): the disassembled `AppleT7000PMGR::initRegGroups()`
(inherited by `AppleT7001PMGR`, both in the same repo's
`kexts/10.3/s8000/AppleT7001PMGR.kext`) sets up register groups at offsets
`0x10218`, `0x1e000`, `0x2d000`, `0x30000`, `0x32000` from a `RegMap`
base -- and the real ADT's own `pmgr` node (`AAPL,phandle 0x1a`, matching
KLCT's provider) has `reg = 00 00 00 0e 00 00 00 00 00 00 04 00 ...`,
which decodes (same little-endian, low-32-bits-plus-implied-`0x2`-prefix
convention this project already uses for every other T7001 device, e.g.
`spi3`'s own ADT `reg` bytes reverse-engineer cleanly against its
already-known-correct `0x2 0x0a08c000` DTS value) to **physical base
`0x20e000000`, size `0x40000`** -- exactly the PMGR base already seen
in this session's own DTB dumps (`power-management@20e000000`). Two
completely independent sources (a disassembled proprietary Apple binary,
and this project's own real captured ADT) agree.

**Still open: which real register KLCT's device-index `8` actually is.**
Mainline Linux's own `t7001-pmgr.dtsi` (already in this project's pinned
kernel source, `drivers/pmdomain/apple/pmgr-pwrstate.c`'s device tree)
was checked directly for a matching entry -- it defines `ps_spi0`
through `ps_spi3` (`power-controller@20180`..`@20198`, the same
`ps_spi3` this project already uses and has hardware-proven) but **no
touch/multitouch entry at all**. Device-index `8` is not a raw offset
into this same table (the mainline table's entries are addressed by
fixed byte offset, not small sequential indices), so it doesn't resolve
by inspection alone. The exact mapping is baked into a data table
inside the compiled `ApplePMGR`/`AppleT7001PMGR` binaries that hasn't
been located and decoded yet -- a further, bounded disassembly task
(find the device-descriptor array `_enableDeviceGated`/
`_updateDeviceStatus` index into), not something inferred from what's
been read so far. **Deliberately not guessed at.**

**What this means for scope:** the originally-planned "fresh IPSW
extraction of an older iOS build" turned out to be unnecessary --
everything above came from re-reading a public repo already cited in
this document, at essentially no cost (a few MB, no device connection).
If KLCT's device-table mapping is pursued further, it's more disassembly
of what's already fetched, not a new download.

### What `apple_z2` actually requires -- read from the driver, not assumed

| Requirement | Source | J81 status |
| --- | --- | --- |
| `compatible` in **both** match tables | driver | **see the crash note below** |
| `reset-gpios` | binding, `devm_gpiod_get(dev, "reset", ...)` | AP GPIO82, decoded |
| `interrupts` | binding, `devm_request_threaded_irq(..., spi->irq, ...)` | AP GPIO84 edge, decoded; `interrupts-extended` on the GPIO controller, not AIC |
| `firmware-name` | binding, `device_property_read_string` | TOUCH-3 (IPSW extraction) |
| `touchscreen-size-x` / `-y` | binding `required:`, `touchscreen_parse_properties()` | **unknown** -- see candidates above |
| `apple,z2-cal-blob` | binding, optional | maps onto the ADT's `multi-touch-calibration` |
| `spi-max-frequency` | standard SPI peripheral property | **no ADT source found** -- see below |

**A concrete crash to avoid.** `apple_z2_probe()` does:

```c
z2->input_dev->name = (char *)spi_get_device_id(spi)->driver_data;
```

with no NULL check. For a DT-probed SPI device the SPI core matches
`spi_device_id` entries by modalias -- the compatible string with its vendor
prefix stripped -- which is exactly why the existing entries are named
`j293-touchbar` rather than `apple,j293-touchbar`. Adding a J81 compatible to
`apple_z2_of_match[]` **only** would therefore leave `spi_get_device_id()`
returning NULL and dereference it immediately. TOUCH-2 must add the
compatible to `apple_z2_of_id[]` as well, with a `.driver_data` string for
the input device name.

### Where the SPI clock rate is *not*

Searched the whole ADT: the only `spi-frequency` property on the entire
device is on the `mesa` Touch ID node (`0x007a1200` = 8 MHz). The
`multi-touch` node has none. So the touchscreen's clock rate is not
available the easy way, and is most likely inside its packed `reg` -- note
that `mesa` carries *both* an explicit `spi-frequency` and a packed `reg` of
the same shape, which is what makes `mesa` a useful Rosetta stone for that
encoding if it is ever needed:

```
mesa         reg sizes:  0x000001f4  0x08010100  0x00000000  0x00000014 ...
multi-touch  reg sizes:  0x0000007c  0x08010000  0x00001388  0x00002710 ...
```

The near-identical second cell (`0x08010100` vs `0x08010000`) suggests a
packed configuration word rather than a frequency, and no cell in either
node reads as a plausible frequency in Hz. Deliberately not guessing
further: `spi-max-frequency` for TOUCH-2 should come from Apple's driver
personality data, or start at a deliberately conservative value, rather than
from pattern-matching these cells.

### The calibration blob has a clean home

The binding documents `apple,z2-cal-blob` as "Calibration blob supplied by
the bootloader". On this device that data already exists as the ADT's
`multi-touch-calibration`, and m1n1 is what performs the ADT-to-FDT
translation. That is the natural injection point, and it means the
calibration can reach the driver **without ever being committed to this
repository** -- the same discipline already applied to it during decoding.

None of this blocks TOUCH-1, which only needs the SPI3 *controller* node --
already fully evidenced above.

## TOUCH-1 implementation notes

**Base for the controller port, corrected from the bring-up plan doc**: the
2026-09-08 "Priority review" section says to port from Hoolock's `tests/spi`
branch (`0019398`). Checked both branches directly (GitHub API, not just the
docs) before writing anything: `0019398` is 645 lines with no S5L-specific
register-bit definitions beyond a bare enum case; `tests/kat-spi`
(`c065201`, whose parent already carries a fuller base) is 770 lines with a
real `APPLE_S5L_SPI_CFG_*` bitfield definition set. This matches the
*earlier*, more detailed "Phase 4" section's own characterization
("`tests/kat-spi` ... has a more complete old-controller variant") --
that section was right, the later "Priority review" section's citation was
not. Porting from `c065201`, not `0019398`; flagging this correction in
`docs/plans/2026-09-08-ipad-air2-driver-bringup.md` as well.

**Confirmed real compatible string**: `apple,s5l8960x-spi`, `.data =
APPLE_SPI_TYPE_S5L` (read directly from `c065201`'s own
`apple_spi_of_match[]`, not invented).

**Confirmed real cleanup needed** (matches the bring-up plan's own warning,
now with the actual lines identified): `c065201` prints `dev_info()` on
every single transfer completion and poll iteration -- would flood dmesg in
normal use, needs removing or downgrading to `dev_dbg()`. It also has a
genuine bug-class hack: a bare global `bool defered = false;` that makes
`apple_spi_probe()` unconditionally return `-EPROBE_DEFER` on its *first*
call ever (module-wide, not per-device) and proceed normally after. This is
being dropped entirely, not ported -- if a real probe-ordering dependency
exists on this board, it needs to surface as a genuine failed resource
lookup returning `-EPROBE_DEFER`, not a one-shot global hack.

## TOUCH-1 execution plan and result, 2026-09-10

The remaining TOUCH-1 step -- wiring `0007`/`0008`/`0009` into
`kernel/hoolock.nix` and running a real cross-build -- was reviewed from
several angles before doing it, because the situation changed since this
document was written: the battery now works on real hardware, so there is a
known-good payload to protect that did not exist on 2026-09-09.

### Angle 1: main payload, or a separate touch-only payload?

**Chose the main `kernel/hoolock.nix`,** matching the BT-1/BAT-1/CHG-1
precedent and this document's own instruction, rather than adding a second
parallel kernel + payload output.

The argument for a separate output was protecting the working battery
payload. It does not hold up: **nothing in this project's boot chain is
flashed or persistent.** Every boot is a fresh checkm8 -> PongoOS -> m1n1
RAM boot, so "recovering" from a bad touch payload means booting the previous
payload -- no recovery procedure, no state to repair. Against that, a second
kernel variant doubles both cross-build time and builder-VM store usage, and
2026-09-10's build session established that store headroom on that VM is a
real, binding constraint (a 40 GB disk needed a garbage collection *and*
`CONFIG_DEBUG_INFO` disabled before a kernel would link at all). Paying that
cost permanently to avoid a problem that a reboot already solves is the wrong
trade.

### Angle 2: can enabling SPI3 hang the boot rather than just fail?

The failure mode that would genuinely hurt is a register access against an
unpowered or unclocked block -- Apple SoCs fault or hang on those, which
would take the working battery down with it rather than degrading politely.

Checked rather than assumed: `0008`'s `power-domains = <&ps_spi3>` resolves,
in the actually-built DTB, to a real and *distinct* PMGR node --
`power-controller@20198`, `#power-domain-cells = <0>`, `label = "spi3"` --
not an alias of another peripheral's domain. Linux's genpd powers a device's
domain on before its driver probes, so the block is live before
`apple_spi_probe()` touches a register. Every other plausible failure
(missing clock, IRQ request failure, controller registration failure)
degrades to a logged probe error on an unrelated subsystem, which cannot
affect the HDQ/battery path.

### Angle 3: kernel configuration

No `patchedHoolockConfig` change is needed. `CONFIG_SPI_APPLE=y` is already
set in the pinned upstream `config_16k` -- checked directly in the built
config artifact, not assumed. This is unlike BAT-2, whose
`CONFIG_BATTERY_BQ27XXX_HDQ_UART` was a brand-new symbol that had to be
appended because no line existed to flip.

`CONFIG_TOUCHSCREEN_APPLE_Z2` is **not** present in that config and is
deliberately **not** being added here. Nothing would bind to it until
TOUCH-2 adds the touch child node, and enabling a driver with no node to
match is noise, not progress.

### Angle 4: the pinmux value stays provisional

`APPLE_PINMUX(51, 1)` is kept exactly as-is. BAT-4 disproved the theory that
the ADT flags word's low byte is the pinmux selector, which is what
originally motivated the value -- but BAT-4 also landed on function **1** for
GPIO34, so function 1 is not contradicted, merely no longer supported by the
reasoning that produced it. Changing it now, blind, would trade one
unverified value for another. The live A/B test this document already
requires remains the way to settle it.

### What this build does and does not prove

Proves: the ported S5L controller code compiles under this project's real
cross-toolchain; the three patches stack cleanly on the current tree
alongside BT-1/BAT-1/2/3 and CHG-1; the resulting DTB carries an enabled
SPI3 node with the right register window, IRQ and power domain.

Does **not** prove: that the controller probes on real silicon, that GPIO51
function 1 is correct, that a `/sys/class/spi_master/` entry appears, or
anything touch-specific. Those are the hardware gate, not this step.

### Result: passed, 2026-09-10

`nix build .#packages.x86_64-linux.m1n1-hoolock-control` succeeded end to end
with `0007`/`0008`/`0009` applied. Verified, rather than assumed from the
exit code:

| Check | Result |
| --- | --- |
| Cross-build of the full payload | exit 0 |
| S5L code genuinely compiled in, not just patched into a file | `apple_s5l_spi_irq` present in the built `System.map`, alongside `apple_spi_probe`/`apple_spi_irq`/`apple_spi_transfer_one` |
| `CONFIG_SPI_APPLE` actually built | kconfig answered `SPI_APPLE, ALTS: Y/n/m` during configure |
| DTB node | `spi@20a08c000`, `compatible = "apple,s5l8960x-spi"`, `reg = <0x2 0xa08c000 0x0 0x4000>`, `interrupts = <0 0x9b 4>` (155), `status = "okay"` |
| Power domain resolves correctly | phandle -> `power-controller@20198`, `label = "spi3"` -- the distinct SPI3 domain, not an alias |
| Pinctrl resolves correctly | phandle -> `spi3-pins { pinmux = <0x10033> }` |
| Both patch guards | `kernel/test_spi_s5l_patch.py` and `kernel/test_hdq_uart_patch.py` pass |

A useful cross-check fell out of the pinmux encoding: `0x10033` is
`(function 1 << 16) | pin 51`, and the neighbouring UART5 group in the same
DTB reads `0x10022` = `(function 1 << 16) | pin 34` -- the exact value BAT-4
proved correct on hardware. SPI3 CS0 is therefore expressed in the same form
that is known-good for this SoC, which is not proof that function 1 is right
for *this* pin, but does rule out an encoding mistake as a failure mode.

Payload `m1n1-linux.bin` SHA-256:
`a363dda168e961a3aa81d810ff301b5e08c74e1656fb9bb68784288d144ac24a`.

**Note for the hardware gate:** this payload contains everything the
known-good battery payload has (BT-1, BAT-1/2/3, CHG-1) plus SPI3. Nothing is
flashed, so if it misbehaves, booting the previous payload
(`0681c720ec632fc6...`) restores the working state with no recovery
procedure.

### TOUCH-1 hardware gate: passed, 2026-09-12

Booted this exact payload on real J81 hardware. First check
(`dmesg | grep -i spi`, `ls /sys/class/spi_master/`) looked like a miss --
zero dmesg lines, only a `spi0` entry, no `spi3`. That reading was wrong, not
the result: `apple_spi_probe()` (as cleaned up in `0007`, which dropped the
per-transfer `dev_info()` spam) never logs anything at all on a *successful*
probe, and the driver does not consult the DT's `spi3` alias to number the
bus -- it lets the SPI core assign the next free number, which is `0` because
this is the only SPI controller that has ever probed in this system.

Verified directly before concluding anything:

```
$ readlink -f /sys/class/spi_master/spi0
/sys/devices/platform/soc/20a08c000.spi/spi_master/spi0
```

That is our SPI3 node (`20a08c000` is its exact register base), definitively.
Further confirmation from the live sysfs tree:

- `driver -> .../bus/platform/drivers/apple-spi`, and the device's own
  `uevent` shows `DRIVER=apple-spi` -- the platform driver bound and
  `apple_spi_probe()` returned success.
- `supplier:platform:20e000000.power-management:power-controller@20198` and
  `supplier:platform:20e300000.pinctrl` both present as reverse-dependency
  links -- the power domain and pinctrl (`APPLE_PINMUX(51, 1)`) resources
  this doc worried about both resolved and were consumed before probe, not
  skipped.
- No new dmesg errors of any kind after the boot banner; the already-working
  battery driver is unaffected (still reporting a plausible reading); uptime
  reached 4 minutes with no hang, crash, or DART fault storm -- the
  "Angle 2" concern from the execution-plan section above did not
  materialize.

**This clears TOUCH-1 entirely.** The controller genuinely probes on real
silicon: clocks, the verified-distinct power domain, and the provisional CS0
pinmux all resolved correctly enough for `devm_spi_register_controller()` to
succeed. What is *not* yet tested is CS0 actually transacting with a real
device, since no touch child exists yet -- that is TOUCH-2's job, and the
first thing to watch for once a child is added.

One cosmetic, non-blocking note for whoever writes TOUCH-2: `apple_spi_probe()`
does not call `of_alias_get_id()`/set `ctlr->bus_num` from the DT's `spi3`
alias, which is why this registers as `spi0` rather than `spi3`. Purely
cosmetic (bus numbering is functionally arbitrary), not worth a patch on its
own, but worth knowing so a future `spidev`/`apple_z2` binding path isn't
written assuming `/dev/spidev3.0`.

### CS0 pinmux: hardware-confirmed, same session, 2026-09-12

The provisional `APPLE_PINMUX(51, 1)` this document flagged as needing a
live A/B test is now settled without needing one, from the *live* pinctrl
debugfs on the same booted session (`for f in
/sys/kernel/debug/pinctrl/*/pinmux-pins; do grep '^pin 51 ' "$f"; done`):

```
pin 51 (PIN51): device 20a08c000.spi function periph1 group PIN51
```

Function 1 is claimed by our own SPI3 device at the hardware level, not just
asserted in the DTB -- the same class of evidence BAT-4 relied on for
GPIO34. No A/B test needed; the provisional value was right.

Also read the four touch-specific pins' live baseline while the session was
open, purely to document a clean starting point for TOUCH-2 (none of this
was expected to show anything, and it didn't):

```
pin 55 (display_sync): UNCLAIMED
pin 82 (reset):         UNCLAIMED
pin 84 (irq):           UNCLAIMED
pin 95 (ldo enable):    UNCLAIMED
```

No conflicts, nothing else has claimed them. System remained healthy
throughout (16 minutes uptime, battery still reporting a plausible value, no
new dmesg errors) -- this was a pure read, no register writes, no reboot.

## TOUCH-2 groundwork, 2026-09-12: what's implemented, what's still deliberately missing

Split into a certain piece (implemented, compile-verified, wired into the
build) and an uncertain piece (documented as a draft only, not written as a
real patch, not wired in), matching the boundary this project draws between
"resolved by evidence" and "would require a guess."

### Implemented: `apple_z2` now knows about J81

`kernel/patches/0011-touchscreen-apple-z2-add-j81.patch` adds
`apple,j81-touchscreen` to **both** of `apple_z2`'s match tables --
`apple_z2_of_match[]` (DT compatible matching) and `apple_z2_of_id[]` (SPI
modalias matching, needed because DT-probed SPI devices match by modalias
and `apple_z2_probe()` dereferences `spi_get_device_id(spi)->driver_data`
with no NULL check; an entry in only one table is a real crash, not a
harmless non-match -- this exact gotcha was found reading the driver on
2026-09-10, now acted on). `CONFIG_TOUCHSCREEN_APPLE_Z2=y` and its parent
`CONFIG_INPUT_TOUCHSCREEN=y` are both now set in `patchedHoolockConfig`
(neither existed as an enabled line in the pinned upstream config; the
first needed appending, same as `CONFIG_BATTERY_BQ27XXX_HDQ_UART`, the
second needed flipping from its existing disabled line). Cross-build
verified this compiles under the real toolchain, matching TOUCH-1's rigor.

This patch is inert on its own: no touch child DT node references
`apple,j81-touchscreen` yet, so nothing changes on the currently-running
hardware or dmesg output. It is safe to ship ahead of the child node because
it only adds table entries a real match still has to select.

### Deliberately not implemented: the child DT node itself

A draft, for review, **not** written as a patch file and **not** wired into
`kernel/hoolock.nix`:

```dts
&spi3 {
	touchscreen@0 {
		compatible = "apple,j81-touchscreen";
		reg = <0>;
		reset-gpios = <&pinctrl_ap 82 GPIO_ACTIVE_LOW>;
		interrupts-extended = <&pinctrl_ap 84 IRQ_TYPE_EDGE_FALLING>;
		/* firmware-name: TOUCH-3 (local IPSW extraction, not committed) */
		/* touchscreen-size-x, touchscreen-size-y: NOT confirmed -- see
		 * "Narrowed: KLCT" above. 5000/10000 are a shape-only guess from
		 * the ADT reg blob's own words and must not be used without
		 * independent confirmation. */
	};
};
```

Why this stays a draft rather than a real, disabled-but-present patch:
turning it on would fail for at least three *compounding, unresolved*
reasons at once (no firmware, no confirmed touchscreen size, and the
Lump-encoded analog rail/KLCT power sequence never implemented) -- a bad
experimental setup, since a failure wouldn't tell us which of the three
actually mattered. `reset-gpios`/`interrupts-extended` themselves are solid
(GPIO82/84, both confirmed unclaimed and matching the ADT
byte-for-byte), but writing the whole node now would invite enabling it
before the other pieces are ready.

**Concrete remaining gates for TOUCH-2, in order:**

1. `KLCT` argument decode (needs a fresh local IPSW extraction of an older
   iOS build with J81/J82 personality code still present -- see above).
2. `touchscreen-size-x`/`-y` real values -- likely resolvable from the same
   `AppleMultitouchSPIJ82` personality data as (1), given the doc's existing
   note that the personality is already identified (`multi-touch,j82`,
   15 ms reset delay, parser type 1, parser-options 16, touch-size ID 3,
   firmware merge name `C1F15,2`) -- "touch-size ID 3" plausibly indexes a
   table this same extraction would reveal.
3. TOUCH-3's firmware extraction, needed either way before a real probe can
   complete.
4. Only then: write the real patch, wire it in, cross-build, and test on
   hardware -- by which point a genuine single-variable test is possible.
