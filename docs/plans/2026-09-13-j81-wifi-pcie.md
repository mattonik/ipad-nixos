# J81 WiFi over PCIe: focused plan

Date: 2026-09-13

Target: iPad Air 2 Wi-Fi, J81/J81AP, A8X/T7001

Status: **evidence captured; compile-only skeleton built; window roles only
partly resolved.** Real J81 ADT evidence for the `apcie` PCIe host controller
is captured and cross-validated. An inert driver and disabled topology are
cross-build verified in a separate package. The window-role review below
identifies the ECAM and shared controller/PHY-interface blocks, but it also
shows why the remaining small-window roles and H9P register offsets must not
be guessed. **No hardware has been touched.**

## Why WiFi, now

Chosen over continuing the touch investigation: touch input has no UI to
exercise yet on this project (no display/desktop environment), so
finishing TOUCH-2/3 wouldn't be independently useful in the near term.
Network access is useful on its own, even from a plain console/SSH
environment -- and unlike touch's remaining KLCT register-offset mystery
or Bluetooth's PMU write-protocol mystery, WiFi has **no equivalent
mystery**: the chip identity, protocol and Linux driver all already
exist and are well understood. The open work is host-controller
bring-up, not reverse-engineering.

## What this project already knew, before today

`research/driver-gap.md`, `research/feasibility.md` and
`research/hardware.md` already established, from the **public J82 ADT**
(a sibling board, not this project's own captured evidence):

- WiFi is **BCM4350 over T7000 PCIe port 1**, not BCM4354 over SDIO --
  this explicitly *invalidated* an earlier, wrong SDIO-based plan.
  UART2 is a control/sideband path only, not a data bus.
- Predicted resources: PCIe port 1 at 2.5 GT/s, wake GPIO165, CLKREQ
  GPIO174, PERST GPIO179, a DART at `0x602002000`/IRQ216.
- `brcmfmac`'s PCIe support (including BCM4350) already exists in
  Hoolock's kernel tree, just not enabled in the current config
  (`CONFIG_CFG80211`/`BRCMFMAC`/`BRCMFMAC_PCIE` all off).
- The real prerequisite is the T7000 PCIe **host controller** itself --
  nothing in the current kernel or DTS describes it at all.

## Real J81 ADT evidence, 2026-09-13 -- confirms every J82 prediction

Read directly from this project's own private capture
(`artifacts/adt/20260908T082112Z-j81.adt`, git-ignored). All of the
following is from the real board, not inferred from J82.

### `wlan-pcie,bcm4350` (grandchild of `apcie`, under `pci-bridge1`)

Confirms the actual WiFi endpoint: `compatible = "wlan-pcie,bcm4350",
"wlan-pcie,bcm"`, `device_type = "pcie-device"`, `iommu-parent = 0x78`
(→ `mapper-apcie1`, below), plus PCIe tuning properties
(`pci-aspm-default`, `pci-max-latency`, `pci-l1pm-control`,
`~cpie-l1ss-workaround`). The real `wlan.*` properties elsewhere in this
node's parent scope (`wlan.background-scan-cache`,
`wlan.tx-power-cap-ctrl`, `wlan.bss.5GHz-preference`, `wlan.awdl.params`,
etc.) are BCM4350 firmware/NVRAM configuration -- not needed for basic
bring-up, but real data if calibration is ever needed later.

| --- | --- | --- |
| `compatible` | `dart,t7001`, `dart,s5l8960x` | Real Linux DT binding-shaped compatible strings |
| `interrupts` | `0xd8` (216) | **Matches the J82-predicted IRQ216 exactly** |
| `page-size` | `0x1000` (4 KB) | Standard |

| `stt-idx-width` | `0xa` (10) | |

`mapper-apcie1` is the DART's mapper child (`reg = 0`, straightforward).

### Register windows: `apcie`'s 12-entry `reg` property, decoded

`apcie`'s `reg` property has **12 entries**, not the single
address+size pair most other nodes in this project have had. Decoded
carefully -- verified the parsing method first against `spi3`'s already
publicly-proven-correct encoding before trusting it on new data, then
cross-checked the same 4-word native layout against `dart-apcie1`'s own
(single-entry) `reg`.  The words are low address, high address, low size and
high size; the constant high address word `0x6` is part of the 36-bit physical
address, not a region attribute:

```
entry  0: 0x610000000, 16 MiB  -- config space (ECAM-shaped)
entry  1: 0x601004000, 4 KiB   -- port 1, region A
entry  2: 0x601001000, 4 KiB   -- port 1, region B
entry  3: 0x602004000, 4 KiB   -- port 2, region A
entry  4: 0x602001000, 4 KiB   -- port 2, region B
entry  5: 0x603004000, 4 KiB   -- port 3, region A
entry  6: 0x603001000, 4 KiB   -- port 3, region B
entry  7: 0x604004000, 4 KiB   -- port 4, region A
entry  8: 0x604001000, 4 KiB   -- port 4, region B
entry  9: 0x600000000, 8 KiB   -- shared
entry 10: 0x601005000, 4 KiB   -- port 1, region C
entry 11: 0x603005000, 4 KiB   -- port 3, region C
```

Clean, obviously-intentional structure: one large config-space region,
then per-port-indexed sub-regions (the port number literally appears in
the offset, e.g. `0xN004000`/`0xN001000`/`0xN005000` for port `N`) --
**but only ports 1 and 3 have a third ("region C") sub-region**, which
is worth understanding rather than assuming is a transcription artifact.
The PCI `ranges` property is also decoded below; it describes endpoint BAR
apertures and does not change these controller addresses.

## Reference driver research

- **Mainline Linux's `pcie-apple.c`** (`drivers/pci/controller/pcie-apple.c`,
  already in Hoolock's pinned kernel source): confirmed wrong generation.
  Its `of_device_id` table only lists `apple,t6020-pcie` and
  `apple,pcie` (T8103/M1-baseline) -- nothing for `apcie,t7000` at all.
  Not usable even as a loose skeleton without heavy rework; this
  project's own driver-gap research already flagged this as only the
  "preferred integration point *if* its controller model fits" -- it
  doesn't.
- **Corellium's `pcie-hx.c`** (`linux-sandcastle`, `sandcastle-5.4`
  branch, `drivers/pci/controller/pcie-hx.c`, 873 lines, fetched and
  read this session): `compatible = "hx,pcie-h9p"` -- a real, working,
  open-source driver for the *structurally* related older-generation
  Apple PCIe controller family (H9P, a different but related SoC
  generation to T7001/A8X). Confirms the overall shape: `NUM_PORT = 4`,
  `NUM_MSI = 32` (both match our real `#ports`/`#msi-vectors` exactly),
  a `mmio[4 + NUM_PORT]` register-window layout (1 config + 3 shared PHY
  + `NUM_PORT` per-port regions), GPIO-based PERST/CLKREQ via
  `devm_gpiod_get_index`, and its own lightweight "SART" IOMMU
  mechanism (simpler than a full DART). This project's own driver-gap
  research already correctly flagged that "its H9P hard-coded tunables
  cannot be reused on A8X" -- confirmed: T7001 needs its own
  `apcie-config-tunables` (now captured above), and T7001's real
  register layout (12 windows, per-port-indexed) differs in detail from
  H9P's hardcoded 1+3+4 grouping, so this is a **structural guide, not
  a drop-in port**. T7001 also uses a real DART (already has a DART
  driver family in this project's kernel, since ANS1 work already uses
  `drivers/soc/apple` mailbox/DART-adjacent infrastructure), not H9P's
  simpler SART -- another real difference to account for, not copy
  blindly.

## What's solid vs what's still open

**Solid** (real ADT evidence, most of it independently cross-validated):
compatible string, port count, IRQ numbers, DART presence and its own
IRQ/compatible/page-size, the wake/CLKREQ/PERST GPIO numbers and link
speed (all matching prior J82-based predictions exactly), the PMGR
power/clock gate indices (cross-validated against real firmware strings
found separately today), the real per-board PHY tuning blob, and the
12-entry register-window count and relative structure.

### Execution update, 2026-09-13: apertures and DART are no longer open

The private J81 capture was decoded using its native low/high address-pair
encoding.  The PCI `ranges` property resolves to a 64-bit prefetchable
aperture from PCI `0x620000000` to CPU `0x620000000`, size `0x1a0000000`, and
a non-prefetchable aperture from PCI `0xc0000000` to CPU `0x7c0000000`, size
`0x40000000`.  The twelve controller windows are absolute addresses, including
the 16 MiB configuration aperture at `0x610000000` and the 8 KiB shared window
at `0x600000000`; their complete list is in
`docs/plans/2026-09-13-pmic-pcie-execution.md`.

The pinned Hoolock kernel already builds the old-Apple DART implementation
for `apple,s5l8960x-dart`.  The J81 ADT `dart,t7001` / `dart,s5l8960x`
strings must be converted to that kernel's conventional compatible spelling
when a disabled topology is added.  DART driver availability is therefore not
a missing implementation task.

An inert `CONFIG_PCIE_APPLE_T7000` skeleton now exists in a separate
`hoolock-pcie-check-kernel` package.  It validates the expected twelve DT
windows/four port interrupts, then returns `-EOPNOTSUPP`; it has no DT node,
is not included in a payload, and does not access hardware.  Its patch applies
cleanly to pinned Hoolock source.  **Cross-build verified, 2026-09-14**, once
the Linux builder VM was restarted: `nix build
.#packages.x86_64-linux.hoolock-pcie-check-kernel --no-link -L` succeeds,
`pcie-apple-t7000.c` compiles, no errors. See
`docs/plans/2026-09-13-pmic-pcie-execution.md` for the full build record.
These results supersede the two resolved items in the following historical
"Still open" list.

### Window-role checkpoint, 2026-09-15

This review used three primary inputs: the private J81 ADT capture (SHA-256
`cf743765e66a1a5b45cbf4e18c0e5ae21454bb1cb678b66e7007e2db04f5b6c2`),
Hoolock Linux at the pinned revision
`6831bc701a6ce059e71e5aaa9488c9195bea6927`, and Corellium's
`sandcastle-5.4` PCIe driver and H9P DTS at revision
`0c2f7dda13d67bb7e06123df516f8bdb1000a79b`. The resulting mapping is:

| ADT entry | Physical window | Defensible role | Certainty and evidence |
| ---: | --- | --- | --- |
| 0 | `0x610000000`, 16 MiB | PCI configuration/ECAM aperture | **High.** Same address, size and first-resource position as Corellium H9P; the aperture also has the shape required by Hoolock's generic ECAM access. |
| 1, 3, 5, 7 | `0x60N004000`, 4 KiB per port | Per-port auxiliary block A | **Structural only.** The address repeats for all four ports. H9P uses `0x601004000` as a separately mapped SART/NVMMU block, but J81 has all four instances plus an external DART, so calling these SART, PHY, or port-control registers would be an unsupported leap. |
| 2, 4, 6, 8 | `0x60N001000`, 4 KiB per port | Per-port controller block B | **Medium structural confidence; exact function open.** These lie inside the address bands used for H9P and newer-Apple root-port blocks. J81's `apcie-config-tunables` is three `(offset, mask, value)` triplets at offsets `0x90`, `0x130`, and `0x134`, matching three offsets in Corellium's port-tunable table, but the ADT does not associate that blob with one of the two windows. |
| 9 | `0x600000000`, 8 KiB | Shared root-complex/PHY-interface control | **High family-level, incomplete register-level confidence.** Corellium maps the same base as its first shared PHY/link block, but H9P exposes 32 KiB where J81 exposes 8 KiB; Hoolock's newer Apple PCIe binding calls the analogous shared resource `rc`. Corellium's accesses at and above `0x4020` do not fit J81's resource, so only the block class transfers, not the H9P sequence. |
| 10, 11 | `0x601005000`, `0x603005000`, 4 KiB each | Pair-level/odd-port auxiliary blocks | **Low.** Their placement after the `0xN004000` blocks and presence only for port groups 1/2 and 3/4 supports a pair-shared interpretation. No reviewed source identifies whether they are PHY, lane, clock, or IOMMU controls. |

The strongest negative result is as useful as the partial mapping: Corellium's
H9P resource order is `config`, three shared PHY/link blocks, then four port
blocks, while J81's ADT interleaves two small windows per port and adds two
odd-port windows. H9P also uses a 16 KiB port block based at `0x60N000000`;
J81 exposes 4 KiB blocks at `+0x1000` and `+0x4000`. Therefore neither H9P's
resource indices nor its register offsets are safe to copy into the T7000
driver.

What is safe to implement next is deliberately narrow: extend the inert
skeleton to validate the twelve **structural slots** and their exact sizes,
without `ioremap`, reads, writes, clocks, IRQ requests, GPIO requests, DART
attachment, link training, or PCI enumeration. Before any functional register
access is added, static analysis of Apple's T7000 `apcie` driver must associate
the two per-port windows and the pair-level windows with actual operations and
decode `dbi-overrides`/`link-state-power`. The existing disabled DT should keep
the unresolved small windows unnamed until then.

**Still open**:
1. The 2026-09-15 checkpoint identifies entry 0 as configuration space,
   entry 9 as shared root-complex/PHY-interface control, and the repeated
   small-window topology. The exact A/B per-port roles and pair-level entries
   10/11 remain unresolved; H9P's actual register use proves its indices and
   offsets are structurally incompatible rather than filling this gap.
2. `t-refclk-to-perst`'s unit (µs vs ms) -- affects real timing in the
   port bring-up sequence.
3. `apcie`'s `dbi-overrides` and `link-state-power` blobs -- present,
   real, not yet decoded; likely needed for correct link training but
   not necessarily for a first compile-only skeleton.

## Basic guidelines: what needs to be done, in order

Matching this project's own established discipline throughout (evidence
before code, isolated non-default payloads before touching the working
default, compile-verify before hardware, hardware tests as their own
separate explicit decision):

1. **Map each of the 12 register windows to its real purpose.** The
   2026-09-15 checkpoint above closes the config/shared classes and records
   the per-port topology. Complete the remaining A/B and pair-level roles by
   statically tracing Apple's T7000 driver; Corellium's H9P indices and offsets
   are now explicitly ruled out as substitutes.
2. **Preserve the disabled DT/DART topology** while its binding is reviewed;
   the Hoolock DART driver is already available for the converted T7001
   compatible. Do not enable the node or attach the DART in functional code.
3. **Keep the DT node** (`t7001.dtsi`: an `apcie` node using the real,
   now-fully-decoded resources; `t7001-air2.dtsi`: enable it and the
   `wlan-pcie,bcm4350` child) -- **disabled/inert by default**, following
   the exact same pattern already proven for UART3/UART5/SPI3 (added to
   the SoC-level dtsi as disabled, enabled only at board level, and even
   then only wired into an isolated test payload, never the default
   `kernel/hoolock.nix`/`m1n1-hoolock-control`).
4. **Extend the compile-only driver skeleton**, structurally adapted from
   `pcie-hx.c` (port count, MSI count, and register layout corrected to
   T7001's real numbers from steps 1-2; DART instead of SART) -- as its
   own dedicated Nix package/payload, exactly the pattern
   `kernel/hoolock-ans1-test.nix` already established for ANS1: never
   touch the default payload, cross-build-verify in isolation first.
5. **Cross-build verify only.** No hardware test at this stage --
   PCIe/DART bring-up is unproven, higher-complexity code; a hardware
   attempt is its own separate, later, explicit decision, same as every
   other risky subsystem in this project (ANS1, the Bluetooth PMU
   write).
6. **Only once the host enumerates on real hardware**: enable
   `CONFIG_CFG80211`/`CONFIG_BRCMFMAC`/`CONFIG_BRCMFMAC_PCIE` (already
   present in Hoolock's kernel source, just off in the current config),
   and extract `brcmfmac4350-pcie` firmware/NVRAM locally from a real
   IPSW (technique already proven and documented this session -- see
   the touch-clock TOUCH-3 sections) -- never commit firmware/NVRAM to
   Git, matching this project's existing rule for all proprietary
   binary data.

No hardware investment is needed for any of steps 1-6; this is pure
software/research work using data and tools already in hand.
