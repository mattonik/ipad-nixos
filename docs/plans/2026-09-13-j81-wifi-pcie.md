# J81 WiFi over PCIe: focused plan

Date: 2026-09-13

Target: iPad Air 2 Wi-Fi, J81/J81AP, A8X/T7001

Status: **six real hardware boots, 2026-09-21 to 2026-09-23, have
conclusively narrowed the cause of an early hang to one untested write
sequence.** `0018`'s driver (both a write-capable and a supposedly
read-only version) hung before reaching a console on real hardware. Five
follow-up payloads (`0019` PMGR-only, `0020` shared-window read, `0021`
ECAM read, `0022` multi-offset ECAM read, `0023` isolated
`pci_host_common_init()`) each individually hardware-verified clean,
proving every piece `pci_host_common_init()` touches -- the DT status
flip, the power-domain attachment, all MMIO reads tried, and the complete
generic PCI bus scan itself -- is safe. The only thing either hanging
attempt did that no clean test did is the actual hardware enable-sequence
**writes** to the shared register window (`REFCLK_EN`, `PERST_INTERNAL`,
the undocumented `0x10c`, `LINK_ENABLE`, the LTSSM-start write), traced
from the real iOS 8.1 kernelcache and never yet tested in isolation.
**Full consolidated findings, including every raw `dmesg` result, in
[`research/t7000-pcie-hardware-findings.md`](../../research/t7000-pcie-hardware-findings.md).**

## Why WiFi, now

Chosen over continuing the touch investigation: touch input has no UI to
exercise yet on this project (no display/desktop environment), so
finishing TOUCH-2/3 wouldn't be independently useful in the near term.
Network access is useful on its own, even from a plain console/SSH
environment -- and unlike touch's remaining KLCT register-offset mystery
or Bluetooth's PMU write-protocol mystery, WiFi has **no equivalent
mystery**: the chip identity, protocol and Linux driver all already
exist and are well understood. The open work is host-controller
bring-up, not reverse-engineering.

## What this project already knew, before today

`research/driver-gap.md`, `research/feasibility.md` and
`research/hardware.md` already established, from the **public J82 ADT**
(a sibling board, not this project's own captured evidence):

- WiFi is **BCM4350 over T7000 PCIe port 1**, not BCM4354 over SDIO --
  this explicitly *invalidated* an earlier, wrong SDIO-based plan.
  UART2 is a control/sideband path only, not a data bus.
- Predicted resources: PCIe port 1 at 2.5 GT/s, wake GPIO165, CLKREQ
  GPIO174, PERST GPIO179, a DART at `0x602002000`/IRQ216.
- `brcmfmac`'s PCIe support (including BCM4350) already exists in
  Hoolock's kernel tree, just not enabled in the current config
  (`CONFIG_CFG80211`/`BRCMFMAC`/`BRCMFMAC_PCIE` all off).
- The real prerequisite is the T7000 PCIe **host controller** itself --
  nothing in the current kernel or DTS describes it at all.

### Register windows: `apcie`'s 12-entry `reg` property, decoded

`apcie`'s `reg` property has **12 entries**, not the single
address+size pair most other nodes in this project have had. Decoded
carefully -- verified the parsing method first against `spi3`'s already
publicly-proven-correct encoding before trusting it on new data, then
cross-checked the same 4-word native layout against `dart-apcie1`'s own
(single-entry) `reg`.  The words are low address, high address, low size and
high size; the constant high address word `0x6` is part of the 36-bit physical
address, not a region attribute:

```
entry  0: 0x610000000, 16 MiB  -- config space (ECAM-shaped)
entry  1: 0x601004000, 4 KiB   -- port 1, region A
entry  2: 0x601001000, 4 KiB   -- port 1, region B
entry  3: 0x602004000, 4 KiB   -- port 2, region A
entry  4: 0x602001000, 4 KiB   -- port 2, region B
entry  5: 0x603004000, 4 KiB   -- port 3, region A
entry  6: 0x603001000, 4 KiB   -- port 3, region B
entry  7: 0x604004000, 4 KiB   -- port 4, region A
entry  8: 0x604001000, 4 KiB   -- port 4, region B
entry  9: 0x600000000, 8 KiB   -- shared
entry 10: 0x601005000, 4 KiB   -- port 1, region C
entry 11: 0x603005000, 4 KiB   -- port 3, region C
```

Clean, obviously-intentional structure: one large config-space region,
then per-port-indexed sub-regions (the port number literally appears in
the offset, e.g. `0xN004000`/`0xN001000`/`0xN005000` for port `N`) --
**but only ports 1 and 3 have a third ("region C") sub-region**, which
is worth understanding rather than assuming is a transcription artifact.
The PCI `ranges` property is also decoded below; it describes endpoint BAR
apertures and does not change these controller addresses.

## Reference driver research

- **Mainline Linux's `pcie-apple.c`** (`drivers/pci/controller/pcie-apple.c`,
  already in Hoolock's pinned kernel source): confirmed wrong generation.
  Its `of_device_id` table only lists `apple,t6020-pcie` and
  `apple,pcie` (T8103/M1-baseline) -- nothing for `apcie,t7000` at all.
  Not usable even as a loose skeleton without heavy rework; this
  project's own driver-gap research already flagged this as only the
  "preferred integration point *if* its controller model fits" -- it
  doesn't.
- **Corellium's `pcie-hx.c`** (`linux-sandcastle`, `sandcastle-5.4`
  branch, `drivers/pci/controller/pcie-hx.c`, 873 lines, fetched and
  read this session): `compatible = "hx,pcie-h9p"` -- a real, working,
  open-source driver for the *structurally* related older-generation
  Apple PCIe controller family (H9P, a different but related SoC
  generation to T7001/A8X). Confirms the overall shape: `NUM_PORT = 4`,
  `NUM_MSI = 32` (both match our real `#ports`/`#msi-vectors` exactly),
  a `mmio[4 + NUM_PORT]` register-window layout (1 config + 3 shared PHY
  + `NUM_PORT` per-port regions), GPIO-based PERST/CLKREQ via
  `devm_gpiod_get_index`, and its own lightweight "SART" IOMMU
  mechanism (simpler than a full DART). This project's own driver-gap
  research already correctly flagged that "its H9P hard-coded tunables
  cannot be reused on A8X" -- confirmed: T7001 needs its own
  `apcie-config-tunables` (now captured above), and T7001's real
  register layout (12 windows, per-port-indexed) differs in detail from
  H9P's hardcoded 1+3+4 grouping, so this is a **structural guide, not
  a drop-in port**. T7001 also uses a real DART (already has a DART
  driver family in this project's kernel, since ANS1 work already uses
  `drivers/soc/apple` mailbox/DART-adjacent infrastructure), not H9P's
  simpler SART -- another real difference to account for, not copy
  blindly.

### Execution update, 2026-09-13: apertures and DART are no longer open

The private J81 capture was decoded using its native low/high address-pair
encoding.  The PCI `ranges` property resolves to a 64-bit prefetchable
aperture from PCI `0x620000000` to CPU `0x620000000`, size `0x1a0000000`, and
a non-prefetchable aperture from PCI `0xc0000000` to CPU `0x7c0000000`, size
`0x40000000`.  The twelve controller windows are absolute addresses, including
the 16 MiB configuration aperture at `0x610000000` and the 8 KiB shared window
at `0x600000000`; their complete list is in
`docs/plans/2026-09-13-pmic-pcie-execution.md`.

The pinned Hoolock kernel already builds the old-Apple DART implementation
for `apple,s5l8960x-dart`.  The J81 ADT `dart,t7001` / `dart,s5l8960x`
strings must be converted to that kernel's conventional compatible spelling
when a disabled topology is added.  DART driver availability is therefore not
a missing implementation task.

An inert `CONFIG_PCIE_APPLE_T7000` skeleton now exists in a separate
`hoolock-pcie-check-kernel` package.  It validates the expected twelve DT
windows/four port interrupts, then returns `-EOPNOTSUPP`; it has no DT node,
is not included in a payload, and does not access hardware.  Its patch applies
cleanly to pinned Hoolock source.  **Cross-build verified, 2026-09-14**, once
the Linux builder VM was restarted: `nix build
.#packages.x86_64-linux.hoolock-pcie-check-kernel --no-link -L` succeeds,
`pcie-apple-t7000.c` compiles, no errors. See
`docs/plans/2026-09-13-pmic-pcie-execution.md` for the full build record.
These results supersede the two resolved items in the following historical
"Still open" list.

### Window-role checkpoint, 2026-09-15

This review used three primary inputs: the private J81 ADT capture (SHA-256
`cf743765e66a1a5b45cbf4e18c0e5ae21454bb1cb678b66e7007e2db04f5b6c2`),
Hoolock Linux at the pinned revision
`6831bc701a6ce059e71e5aaa9488c9195bea6927`, and Corellium's
`sandcastle-5.4` PCIe driver and H9P DTS at revision
`0c2f7dda13d67bb7e06123df516f8bdb1000a79b`. The resulting mapping is:

| ADT entry | Physical window | Defensible role | Certainty and evidence |
| ---: | --- | --- | --- |
| 0 | `0x610000000`, 16 MiB | PCI configuration/ECAM aperture | **High.** Same address, size and first-resource position as Corellium H9P; the aperture also has the shape required by Hoolock's generic ECAM access. |
| 1, 3, 5, 7 | `0x60N004000`, 4 KiB per port | Per-port controller registers | **High.** `AppleEmbeddedPCIEPort` maps resource `2 * port + 1` and applies the fixed port register sequence plus `apcie-config-tunables` through it. |
| 2, 4, 6, 8 | `0x60N001000`, 4 KiB per port | Reserved or other-client register class | **High for the negative result.** The exact iPad5,3 host path has only two `mapDeviceMemoryWithIndex` sites: ECAM index 0 and per-port `2 * port + 1`; neither `AppleEmbeddedPCIE` nor `AppleT7000PCIe` maps these windows during normal host bring-up. Their purpose remains unknown, but they do not block a minimal port-1 path. |
| 9 | `0x600000000`, 8 KiB | Shared root-complex registers | **High.** Apple's driver maps it as `_commonRegistersBaseAddress`. H9P's larger shared block is not register-compatible. |
| 10, 11 | `0x601005000`, `0x603005000`, 4 KiB each | One PHY register block per port pair | **High.** `AppleT7000PCIe::configure` maps them as `_phyBaseAddresses[pair]`. |

The strongest negative result is as useful as the partial mapping: Corellium's
H9P resource order is `config`, three shared PHY/link blocks, then four port
blocks, while J81's ADT interleaves two small windows per port and adds two
odd-port windows. H9P also uses a 16 KiB port block based at `0x60N000000`;
J81 exposes 4 KiB blocks at `+0x1000` and `+0x4000`. Therefore neither H9P's
resource indices nor its register offsets are safe to copy into the T7000
driver.

An exact iPad5,3 iOS 8.1 trace then resolved the Apple-specific details.  The
kernelcache SHA-256 is
`19c277d60e0a1185b1e4a1b72cda4f1f550c0b0bf670791542234a6dbbcc28bf`;
`AppleEmbeddedPCIE.kext` loads at `0xffffff8002be9000` and
`AppleT7000PCIe.kext` at `0xffffff8002e6d000`.  Both `apcie-config-tunables`
and `dbi-overrides` are 12-byte `(offset, clear-mask, set-value)` records.
Apple applies them by read-modify-write through the per-port controller window,
temporarily asserting and restoring DBI write-enable at offset `0xbc`.
`link-state-power` is four residency-energy coefficients for reporting; no
link-training or power-state programming use was found.

What is safe to implement next remains deliberately narrow: validate the
twelve resource start/size pairs in the inert skeleton, without `ioremap`,
reads, writes, clocks, IRQ requests, GPIO requests, DART attachment, link
training, or PCI enumeration. The even-numbered per-port windows should remain
unnamed and unused; the remaining evidence gate is the complete enable order
for DART activation, CLKREQ, PERST and the common-register sequence.

### Enable-sequence checkpoint, 2026-09-21

The matching iPad5,3 iOS 8.1 kernelcache confirms that `AppleT7000PCIe`'s
`_enablePortHardware` uses the shared window for port `p` as follows: clear
bit 0 at `0x118 + p * 0x80`; when an internal reference clock is used, set bit
0 at `0x108 + p * 0x80`; delay 10 microseconds; clear bit 0 at
`0x10c + p * 0x80`; set bit 0 at `0x100 + p * 0x80`; optionally set bit 20 at
that last register for `muxed-auxclk-auto-dis`; delay `t-refclk-to-perst`
(100 microseconds on J81); set bit 0 at `0x118 + p * 0x80`; clear bit 8 at
`0x108 + p * 0x80`; then write 3 at `0x820 + p * 0x40`.

The unit is exact rather than inferred: the called kernel symbol at
`0xffffff80023a3be0` is `_IODelay`, whose argument is microseconds. The
high-level `AppleEmbeddedPCIEPort::enableGated` path at
`0xffffff8002bee6cc` establishes the surrounding order:

1. call `_enablePortHardware(p)` and repeat the final shared-register write of
   3 at `0x820 + p * 0x40`;
2. invoke `function-dart_force_active(1)` and the optional NVMe-MMU equivalent;
3. discover the PCI capability offsets, apply the maximum-link-speed setting,
   root/port `dbi-overrides` and `apcie-config-tunables`, then program config
   space and MSI state;
4. transition the software state to enabling;
5. call `setEndpointReset(0)`, which invokes `function-perst(0)` and therefore
   deasserts PERST; then set bit 0 of port config register `0x80` to start the
   link attempt.

The constructor acquires and retains `function-clkreq`, but an exhaustive
instruction search of `AppleEmbeddedPCIE.kext` finds no later load or call of
that object. Apple's host path therefore does not explicitly toggle CLKREQ;
the signal remains endpoint/controller managed. No controller register was
read or written on J81 for this result.

**Still open**:
1. The purpose of entries 2/4/6/8 is unknown, but Apple’s normal host path
   does not map them; keep them reserved and unused.
2. The semantic names of the shared-register bits remain unknown even though
   their offsets, values and order are now exact. Preserve the sequence rather
   than assigning guessed clock/reset names.
3. The cold-boot precondition that leaves PERST asserted before
   `enableGated` remains to be expressed explicitly in a Linux implementation;
   the traced enable path proves only its later deassertion.

### Bundled hardware-test boundary, 2026-09-21

The next payload should be one isolated **PCIe link/enumeration** test, not a
general WiFi payload.  It can collect all useful host evidence in one boot:

1. the T7000 driver's validated resource map and probe milestones;
2. the exact recovered port-1 controller sequence, including the two
   microsecond delays;
3. DART-force-active success or failure;
4. PERST deassertion and link-start result; and
5. root-bus enumeration, PCI vendor/device ID, and BCM4350 chip revision.

This is the smallest experiment that answers the remaining WiFi question.
It must retain the normal USB-network debug shell and print a concise final
result to `dmesg`; a failed link must leave it possible to recover and inspect
logs over USB.  It must not load `brcmfmac`, upload firmware, associate to an
access point, change charger settings, or touch Bluetooth, touch, storage, or
the default control payload.  Firmware is not required to establish a PCIe
link, so bundling it would only add a second failure source.

The repository's old `boot/extract-firmware.sh` incorrectly described J81 as
BCM4354 over SDIO.  The real ADT says BCM4350 over PCIe.  In the pinned
Hoolock `brcmfmac` source, BCM4350 revisions 0--7 request
`brcm/brcmfmac4350c2-pcie`, while revisions 8--31 request
`brcm/brcmfmac4350-pcie`.  The first payload must therefore record the real
chip revision before the later firmware payload chooses a basename.  Apple
firmware files and board NVRAM remain private, ignored under `firmware/`, and
must be converted from the matching IPSW's raw `firmware/wifi` files rather
than blindly renamed.

This gives two clean tests from one bring-up effort:

| Test payload | Includes | Success evidence | Deliberately excluded |
| --- | --- | --- | --- |
| PCIe link/enumeration | Host driver, disabled-by-default DT enabled only in this payload, DART, port-1 GPIOs, diagnostic logging | Root bus plus BCM4350 PCI ID/revision in `dmesg`/sysfs | `brcmfmac`, proprietary firmware/NVRAM, WiFi association |
| WiFi firmware | The proven host path plus the selected private BCM4350 firmware/NVRAM and `brcmfmac` PCIe | Driver's exact firmware request, `wlan*` interface | Any new controller sequencing or unrelated subsystem change |

The first row still needs implementation and cross-build verification. It is
not safe to generate a hardware payload until that driver code is reviewable;
the present compile-only skeleton remains intentionally inert.

### PCIe link/enumeration test: implemented and cross-build verified, 2026-09-21

Per the approved plan
(`/Users/martinp/.claude/plans/mighty-snuggling-cocke.md`), the compile-only
skeleton (`kernel/patches/0016-...`) is now superseded, for this test
payload only, by a real but strictly bounded driver:
`kernel/patches/0018-pcie-apple-t7000-enumeration-test.patch`, layered on top
of `0016` (same discipline as ANS1's `0012` hardening on top of
`0013`/`0014`/`0015` -- neither earlier patch is edited or removed).

What it does, matching the recovered evidence exactly:

- Uses the kernel's own generic ECAM host-bridge helpers
  (`pci_host_common_init()`, the same `struct pci_ecam_ops`-based approach
  mainline's own `pcie-apple.c` uses -- verified directly against the real
  pinned Hoolock source, not assumed) for config-space access and bus
  enumeration. Config-space reads returning all-Fs if the link never comes
  up is already the natural, standard "no device" signal; no link-status
  register needed decoding.
- Maps only the ECAM window (index 0, handled automatically by the generic
  helper) and the shared root-complex window (index 9). Windows 2/4/6/8
  stay unmapped, matching the confirmed negative result that Apple's own
  host path never touches them.
- Implements the exact recovered `_enablePortHardware` sequence for board
  port 1 only (the only populated port): the two confirmed microsecond
  delays (10 us, then the `t-refclk-to-perst` 100 us), the same register
  offsets and bit positions already documented above.
- **Does not hand-roll PERST# GPIO handling.** Verified directly against
  the real `pci-host-common.c` source: `pci_host_common_init()` already
  calls `pci_host_common_parse_ports()`, which recursively finds any child
  node with `device_type = "pci"` and a `reset-gpios` property and
  deasserts it automatically as part of the generic `pci_host_probe()`
  flow. The DT change below adds exactly that child node (matching the real
  ADT's own `pci-bridge1`-under-`apcie` structure) instead of writing
  driver-side GPIO code.
- Leaves CLKREQ alone entirely, and drops the `msi-controller`/`msi-parent`/
  `msi-ranges` DT properties for this test build specifically (the matching
  driver implements no MSI domain, so declaring one unbacked is worse than
  omitting it -- basic enumeration needs neither).
- DT changes (same isolated-source-copy discipline as every prior DTS
  patch): both the `pcie` and `dart_apcie1` nodes flip from
  `status = "disabled"` to `"okay"`, and a `pci@0,0` child node is added
  under `pcie` carrying `reset-gpios = <&pinctrl 179 GPIO_ACTIVE_LOW>`
  (OIPG pin 179, the already-decoded `function-perst` pin).

New isolated build infrastructure, mirroring `hoolock-ans1-test.nix`/
`m1n1-hoolock-ans1-test` exactly (a real, bootable payload built on the same
proven patch stack `kernel/hoolock.nix` already applies, so it boots with
everything already hardware-proven -- USB networking, RTC, backlight,
battery, working charging -- plus PCIe, never touching the default control
payload's own build): `kernel/hoolock-pcie-test.nix`,
`hoolockPcieTestKernel`/`hoolock-pcie-test-kernel`, and the
`m1n1-hoolock-pcie-test` payload output in `flake.nix`.

**Cross-build verified.** `nix build
.#packages.x86_64-linux.m1n1-hoolock-pcie-test --no-link -L` via the
Linux builder VM produced a complete, real bootable payload (`Pongo.bin`,
`m1n1.bin`, `t7001-j81.dtb`, `Image.gz`, `initramfs.gz`, the assembled
`m1n1-linux.bin`, and `SHA256SUMS` with real checksums for all of them) --
confirmed by listing the actual Nix store output directly, not just
trusting a "build succeeded" line. `dtc` (the device-tree compiler) prints
four new advisory warnings for the added `pci@0,0` node -- three about it
not having its own `#address-cells`/`#size-cells`/`ranges` (dtc's generic
PCI-bridge schema assumes any `device_type = "pci"` node is a full bridge

### Post-attempt implementation review: the diagnostic was not passive, 2026-09-21

The current `0018` driver calls `pci_host_common_init()`. Before that call
returns, the pinned kernel maps ECAM and calls `pci_host_probe()`; the driver
also maps and reads the shared controller window, and supplies generic PCI
configuration read **and write** operations. Thus the third hardware attempt
still performed controller MMIO and PCI configuration-space activity. With no
captured early log, its identical hang cannot distinguish among DART probing,
PMGR power-domain activation, shared-window reads, ECAM access, or generic
PCI probing. Treat the former "read-only diagnostic isolates the DT flip"
statement as superseded.

The review also found two material implementation gaps in the first
write-capable payload:

1. `pci_host_common_init()` does **not** call
   `pci_host_common_parse_ports()` or deassert `reset-gpios`. The helper is
   only a parser for controller drivers that call it explicitly. Therefore
   the `pci@0,0` child in the earlier payload did not deassert PERST, despite
   the old plan text claiming that it did.
2. The implementation covered only Apple's `_enablePortHardware` shared
   register subroutine. It did not map the port window, apply the captured
   DBI overrides or tunables, force the DART active in Apple's order,
   deassert PERST, or set port-window offset `0x80` bit 0 to start the link.
   Generic PCI enumeration cannot substitute for those controller-specific
   steps.

Claude's proposed DART-only/power-domain split is a useful instinct but is
not a sufficient test design. Enabling the existing DART node is active: the
pinned Apple DART driver maps the block, resets it, clears translation state,
and requests its IRQ. The recovered Apple sequence force-activates DART only
*after* port hardware setup, so a standalone early DART reset can itself be
the failure. Conversely, leaving the current PCI driver in a PCIe-only test
would still map ECAM and scan the bus, so it would not isolate the PMGR domain.

The J81 ADT also gives three PCIe gates (`PCIE`, `PCIE_AUX`, `PCIE_REF`), while
the current DT names only `ps_pcie`. The pinned T7001 PMGR topology exposes
separate, non-hierarchical `ps_pcie`, `ps_pcie_aux`, and `ps_pcie_ref` power
states. Whether the latter two must be modeled as domains, clocks, or an
explicit controller operation is an evidence gap that must be resolved before
any further controller MMIO test.

**Better next path, in order:**

1. **Recover the missing dependencies offline.** Trace the iPadOS power-gate
   and `function-dart_force_active` implementations, and recover the
   controller's link-ready/status poll. This establishes the required
   PCIE/AUX/REF ownership and a bounded success/timeout condition.
2. **Make a true PMGR-only payload.** Keep DART disabled, remove the
   `iommu-map`, and use a T7000 platform driver's `.probe` that logs and
   returns without mapping any resource or calling `pci_host_common_init()`.
   Enabling the PCIe node then tests exactly the platform power-domain
   attachment that occurs before `.probe`, while retaining USB recovery.
3. **Only after that boot succeeds**, test controller initialization and stop:
   model the evidenced gates, execute the recovered shared-register sequence,
   and emit a marker before and after each bounded step. Do not map ECAM,
   reset DART, or enumerate PCI yet.
4. **Add DART in Apple's recovered order**, rather than as an early standalone
   probe. Then add DBI/tunables, explicit PERST deassertion, the final port
   `0x80` link-start write, and the recovered link-status timeout.
5. **Enumerate PCI last.** Only after a proven link-ready result should the
   generic ECAM/PCI core and, later, `brcmfmac` be introduced.

No additional hardware boot follows from this review. The current
`m1n1-hoolock-pcie-test` payload is retained as a record of the failed
experiment, not a candidate for another run.

### Step 2: `function-dart_force_active` and gate semantics recovered offline, 2026-09-23

Follow-up source review of the pinned Linux PMGR implementation found that
`ps_pcie`, `ps_pcie_aux`, and `ps_pcie_ref` are independent, non-hierarchical
genpds. The driver follows only explicit DT parent links, and these siblings
have none; therefore `power-domains = <&ps_pcie>` cannot enable AUX/REF.
`0019` proved only `ps_pcie` safe. This is a production-driver dependency,
but it does not block a narrow test of the current Linux DART reset path.

Ghidra analysis of `AppleEmbeddedPCIE.kext` and `AppleS5L8960XDART.kext` from the same pinned iPad5,3 12B410 kernelcache. Full writeup, including the decompiled call sequences, in [`research/t7000-pcie-hardware-findings.md`](../../research/t7000-pcie-hardware-findings.md)'s "`function-dart_force_active` and gate semantics, recovered 2026-09-23" section. Headline findings:

- **The previously-documented order was backwards.** `AppleEmbeddedPCIEPort::enableGated()` calls `function-dart_force_active(true)` *immediately after* requesting the power/clock gate -- before the driver even confirms the gate reports active, and well before any register write to the controller. Apple does not wait for "port hardware setup" first.
- `function-dart_force_active` only has a real effect if the DART's own `_manualAvailabilityEnabled` flag is already true; otherwise `_updateAvailability()` ignores the forced value and re-derives availability from registered IOMMU mapper activity (of which there would be none yet). Where that flag gets set was not traced in this pass -- a real, open gap in the evidence.
- The `power-gates`/`clock-gates` ADT property names never appear by name in the PCIe port driver; only a single gate index (the `power-gates` value, `57`) is referenced by the two gate-enable calls. This implies `PCIE_AUX`/`PCIE_REF` (`58`/`56`) are walked automatically by the underlying PMGR machinery, not by explicit per-gate driver code -- meaning whether Linux's `power-domains = <&ps_pcie>` binding (already proven clean by `0019`) covers all three gates the same way is still an open, unverified assumption that should be checked against the Hoolock kernel's own PMGR/genpd driver source before the next hardware test.

**Correction to the preceding gate inference:** Linux source disproves its claim
that `ps_pcie` can automatically cover all three gates. The discussion of
Apple's possible underlying handling is retained as an Apple-driver lead;
it does not describe the current Linux DT behavior.

**Next controlled experiment**: retain the known-safe `0019` PCIe PMGR-only node, enable `dart_apcie1`, and keep `iommu-map` absent. This changes only stock Linux DART probe/reset while preserving `ps_pcie`; a PCIe-disabled DART-only test would also remove that power state because the DART node has no power-domain reference.    now-fully-decoded resources; `t7001-air2.dtsi`: enable it and the
   `wlan-pcie,bcm4350` child) -- **disabled/inert by default**, following
   the exact same pattern already proven for UART3/UART5/SPI3 (added to
   the SoC-level dtsi as disabled, enabled only at board level, and even
   then only wired into an isolated test payload, never the default
   `kernel/hoolock.nix`/`m1n1-hoolock-control`).
4. **Extend the compile-only driver skeleton**, structurally adapted from
   `pcie-hx.c` (port count, MSI count, and register layout corrected to
   T7001's real numbers from steps 1-2; DART instead of SART) -- as its
   own dedicated Nix package/payload, exactly the pattern
   `kernel/hoolock-ans1-test.nix` already established for ANS1: never
   touch the default payload, cross-build-verify in isolation first.
5. **Cross-build verify only.** No hardware test at this stage --
   PCIe/DART bring-up is unproven, higher-complexity code; a hardware
   attempt is its own separate, later, explicit decision, same as every
   other risky subsystem in this project (ANS1, the Bluetooth PMU
   write).
6. **Only once the host enumerates on real hardware**: enable
   `CONFIG_CFG80211`/`CONFIG_BRCMFMAC`/`CONFIG_BRCMFMAC_PCIE` (already
   present in Hoolock's kernel source, just off in the current config),
   and extract `brcmfmac4350-pcie` firmware/NVRAM locally from a real
   IPSW (technique already proven and documented this session -- see
   the touch-clock TOUCH-3 sections) -- never commit firmware/NVRAM to
   Git, matching this project's existing rule for all proprietary
   binary data.

No hardware investment is needed for any of steps 1-6; this is pure
software/research work using data and tools already in hand.
